# cloudrop 1.0.0 Implementation and Release Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** ship cloudrop 1.0.0. The pilot's workarounds become library features, the public API is frozen under semver,
the floors are Node 26 and TypeScript 7, and the package is released only after the pilot passes on the packed
candidate and the owner says "release".

**Architecture:** five waves.
- **Wave 0** (sequential): the platform floor and the decision files.
- **Wave 1** (sequential): the foundation every later task builds on. The store code moves behind the store object,
  record and API types are tightened, the names are frozen, and typed auth and context land.
- **Wave 2** (parallel, disjoint files): features. Server refusals, the `BUCKET_BLOCKED` classifier, React callbacks,
  owner erasure.
- **Wave 3** (parallel): docs, reference, freeze guard, CI lanes, debts.
- **Wave 4:** review, gates, candidate, pilot, owner. Then the release.

**Tech stack:**
- TypeScript 7, Bun 1.4.4, Node 26, Vitest, Biome, tsdown, size-limit;
- Postgres 18 and SQLite for the store lanes, RustFS, Wrangler, live R2, Playwright Chromium;
- TypeDoc and api-extractor (dev only).

**Spec:** [`docs/superpowers/specs/2026-11-22-1.0.0-design.md`](../specs/2026-11-22-1.0.0-design.md). Read it before any
task. Its part numbers are cited as "spec §N".

## Global Constraints

- **The floors are Node 26 (`engines.node: ">=26"`) and TypeScript 7.0** for the shipped types (owner, 2026-11-22).
  Browsers stay at Chrome 103, Firefox 100 and Safari 16 (`M4-F6`). Client code uses no API newer than that floor.
- **Zero runtime dependencies** in `packages/cloudrop` and web-platform APIs only in `src/`, with the exceptions in
  AGENTS.md (`cloudrop/react` imports `react`; the CLI bin uses Node's `process`).
- **Everything in English:** code, comments, messages, docs and commits. Conversation with the owner is in Polish.
- **Public calls return `{ data, error }`.**
  - The handler never throws.
  - A client receives only `code`, `message`, `retryable`, `parts` and `content` (`M11-K3`; spec §2c adds `content.kind`).
  - Messages never contain credentials, presigned URLs or raw storage responses.
- **The server trusts only the upload token after `/upload`.**
- **Size limits (checked by `bun run check`):** source files at most 250 lines (aim for 200 to 220), `*.test.ts` at most
  400, a function's cognitive complexity at most 15.
- **Tests:**
  - colocated (`foo.ts` beside `foo.test.ts`); the lane is chosen by filename;
  - every test names a contract and an oracle (load `.claude/skills/testing-patterns`);
  - no `retry`, no skip-to-green;
  - Docker containers carry the label `cloudrop.test`;
  - live R2 writes only under `live-test/cloudrop-<random>/`.
- **After writing code and before any review, load `.claude/skills/code-quality`.**
- **Decisions:** a ruling that changes behaviour or a public contract gets an `M12-<letter><n>` entry in the same commit,
  in its series file. Each entry has a decision, a why, an "if wrong", a status and where it is visible.
- **Git:**
  - stage exact paths and use conventional commits;
  - never `git stash`, `reset`, `clean` or `checkout --`;
  - never push except the integration branch's final fast-forward to `main`, which the controller does.
  - Worktrees live in `~/projects/.worktrees/cloudrop/<slug>`, never in `/tmp`. Run `bun install` in each one.
- **Every change appends to `packages/cloudrop/CHANGELOG.md` under `## Unreleased`.** Breaking changes go in its
  "Upgrading to 1.0" list, each with the exact before and after.
- **Lanes:**
  - `bun run verify` for every task;
  - `test:db`, `test:wrangler`, `test:rustfs` and `test:live` for store or storage changes;
  - `test:chaos` for client or server changes;
  - `test:browser` for client, React or example changes;
  - `scripts/check-drizzle-versions.sh` for adapter changes.
  - Parallel tasks use their own ports. Task N uses `CLOUDROP_RUSTFS_PORT=19200+10N`, `CLOUDROP_WRANGLER_PORT=18800+10N`
    and `CLOUDROP_POSTGRES_PORT=19700+10N` (Task 6: 19260, 18860, 19760). Never use 5432 or 55432.
  - `test:browser` and `test:browser:live` bind fixed ports (5173, 5181, 19100, 19610), so only one task at a time runs
    them, and the controller runs them after each merge. Stop the owner's demo first and restart it after.
- **The vstack pilot** (`/home/vcode/projects/vstack`) follows its own AGENTS.md.
  - A push to vstack `master` deploys production at once (Dokploy autoDeploy). Pilot work stays on a branch, unpushed,
    until the owner's go, and a migration goes through the Dokploy migrator before the push.
  - Never run `db:*` against the shared dev database without the owner.

    route: R; owner: string | null; uploadId: string | null; expiresAt: Date; createdAt: Date;

  export interface PendingRecord<R extends string = string> extends RecordBase<R> {

  }
  export interface CompletingRecord<R extends string = string> extends RecordBase<R> {
    status: "completing"; claimedAt: Date; completedAt: null; endedAt: null; cleanedAt: null; result: null;
  }
  export interface CompletedRecord<R extends string = string> extends RecordBase<R> {
    status: "completed"; claimedAt: Date; completedAt: Date; endedAt: null; cleanedAt: null; result: string | null;
  }
  export interface DeletedRecord<R extends string = string> extends RecordBase<R> {
    status: "deleted"; claimedAt: Date; completedAt: Date; endedAt: Date; cleanedAt: Date | null; result: string | null;
  }
  export interface AbortedRecord<R extends string = string> extends RecordBase<R> {
    status: "aborted"; claimedAt: null; completedAt: null; endedAt: Date; cleanedAt: Date | null; result: null;
  }
  export interface ExpiredRecord<R extends string = string> extends RecordBase<R> {
    status: "expired"; claimedAt: null; completedAt: null; endedAt: Date; cleanedAt: Date | null; result: null;
  }
  export interface RejectedRecord<R extends string = string> extends RecordBase<R> {
    status: "rejected"; claimedAt: Date; completedAt: null; endedAt: Date; cleanedAt: Date | null; result: null;
  }
  export type FailedRecord<R extends string = string> = RecordBase<R> &
    { status: "failed"; completedAt: null; endedAt: Date; result: null } &
    ({ claimedAt: null; cleanedAt: Date | null } | { claimedAt: Date; cleanedAt: Date });

  }
