# Plan audit: M3 chaos proxy

Plan `docs/superpowers/plans/2026-11-17-m3-chaos.md` and spec `docs/superpowers/specs/2026-11-17-chaos-design.md`,
audited at `dcf29f8` on `feat/m3-chaos`. While the audit ran, Tasks 3 (`3ab07a6`) and 2 (`0dcd26d`) landed. They were
read too, and one finding (I3) now also touches `docs/decisions/m3-chaos.md`.

Probes, measured 2026-11-17 against `rustfs/rustfs:1.0.5` in a `cloudrop.test`-labelled container, with Node 24.22.2
and Bun 1.4.4. The container was removed and the scratch directory deleted afterwards.

| Probe | Result |
|---|---|
| Single PUT (presigned) and UploadPart answers | `200`, `content-length: 0`, empty body |
| PUT again with `If-None-Match: *` | `412` |
| `GET /<bucket>?uploads&prefix=m` around one multipart upload | 1 before complete, **0 after complete**, 0 without a prefix |
| Open upload, then `DELETE ?uploadId` | 1, then `204`, then 0 |
| `req.socket.resetAndDestroy()` in a `node:http` server, 8 MiB fetch body, reset after 1 MiB | exists in Node 24 and Bun 1.4.4; the client sees `ECONNRESET` (Bun's first chunk was already 1.4 MiB) |
| Server answers `429` + `Retry-After: 2` without reading an 8 MiB fetch body (5 times) | Node fetch reads `429` and `retry-after=2` every time |

## Critical

### C1. "Truncate" as specified does nothing to a PUT, so row 12 tests nothing

- **Where:** Proxy API `{ kind: "truncate" }`. Task 1 says "truncate (headers arrive, the body does not)". Spec §2
  says "forward then cut the answer after its headers". Spec §4 row 12.
- **Evidence:** measured above: RustFS answers PutObject and UploadPart with `200` and `content-length: 0`. Once the
  headers are out, the answer is already complete. `client/transport.ts:46-49` (XHR `onload` with 2xx → stored) and
  `client/bucket.ts:66-70` (fetch `response.ok` → stored).
- **What goes wrong:** both lanes see a complete `200` and count the file stored on the first attempt. No retry
  happens and no `If-None-Match: *` → `412` path runs. The browser row expects a retry, so it fails. The Node row passes
  without proving anything (research row 12 already guessed "fetch transport may already see `ok`").
- **Fix:** define `truncate` as: forward the request, wait for the whole upstream answer (so the bucket has stored the
  bytes), then `resetAndDestroy()` the client socket before writing any byte of the status line. If a cut after the
  headers is still wanted for answers that have bodies (ListParts XML), make it a separate variant:
  `{ kind: "truncate"; at: "beforeHeaders" | "inBody" }`. Task 1's test should then assert that the target received
  the whole request, the client got `ECONNRESET`, and no status reached it. With this fix, row 12 behaves the same in
  both lanes: opaque, `/sign` renewal, retry, `412` (measured), stored. The proxy log shows `PUT object` reset after
  upstream 200, then `PUT object` 412.

### C2. Rows 10, 11 and 17 assume parts of about 1 MiB, but every non-last part is 8 MiB

- **Where:** spec §4 row 11 ("throttle `PUT part 1` to 64 KiB/s … fetch allowance not exceeded"), row 10 ("black hole
  on `PUT part 1` … and Node fetch allowance"), row 17. Plan Task 5b says row 10 runs in Node "only if it fits the
  budget with a small file".
- **Evidence:** `plan.ts:16,39`: `FIRST_PART_SIZE = 8 * MiB`, and `partSize = max(8 MiB, rules.minPartSize)`, so no
  smaller part size exists. `client/transport.ts:22-23,85`: the fetch allowance is `30 000 + size / 102.4` ms.
  `vitest.config.ts:17`: the integration-style timeout is 60 s.
- **What goes wrong:**
  - Row 11 (Node): 8 MiB at 64 KiB/s takes 128 s, but the fetch allowance is 30 + 81.9 = 111.9 s. The client declares
    a stall, which is the opposite of the row's expectation, and the test exceeds its 60 s timeout.
  - Row 11 (browser): 128 s for one row.
  - Row 10 (Node) on part 1 waits 111.9 s before the stall.
  - Row 17 throttles four 8 MiB parts at once.

  The research's "1 MiB body at 64 KiB/s (16 s < 40.24 s)" holds only for a single PUT or a small last part.
- **Fix:** in Node, run row 11 on a 1 MiB single PUT (16 s, allowance 40.2 s) or on a small last part (file 8 MiB +
  1 MiB, throttle `PUT part 2`, 16 s). In the browser, use the same small part, or keep 8 MiB at ≥ 512 KiB/s (16 s).
  Row 10 in Node is a single PUT of ≤ 64 KiB (about 30.6 s) with a per-test timeout ≥ 45 s, or it moves to the soak
  project. State the file size of every row in the plan (see M2).

### C3. Row 7's `retry()` leaves the first ticket's multipart upload open by design, so the plan's universal oracle fails and its bug protocol points the wrong way

- **Where:** spec §4 row 7 ("`retry()` asks a new ticket (M3-U31)") and §4's oracle ("no multipart upload is left
  under the run's prefix" for every done file). Task 5a. Task 5's step "A row that exposes a client or server bug:
  stop … fix it".
- **Evidence:** `client/retry-file.ts:11-17` (`UPLOAD_REJECTED` needs a new ticket); `client/job-run.ts:95-101,108`
  ("No /abort for the old ticket, as for a retry's new ticket (M3-U55)"); `docs/decisions/m3-uploader.md:828`
  (M3-U55).
- **What goes wrong:** after a successful retry, `expectNoUploadsLeft()` finds the first upload. An executor following
  the plan treats this as a client bug and adds an `/abort`, which reverses a decided ruling. The soak (row 18) hits
  the same thing whenever a retry takes a new ticket.
- **Fix:** row 7 asserts exactly one leftover upload under the prefix, the first ticket's, and cites M3-U55. The
  fixture's cleanup aborts it. Spec §4's oracle reads "no upload left except those M3-U55 leaves to the lifecycle
  rule". Task 5a names row 7 as the exception, so nobody "fixes" it.

## Important

### I1. The driver has no ListMultipartUploads, and the plan's instruction for it contradicts itself

- **Where:** Task 4: "`ListMultipartUploads` under the prefix is empty; add a storage call only if the driver lacks
  one, through the existing driver API".
- **Evidence:** `storage/driver.ts:96-153` (`StorageDriver` has `listParts`, `abortMultipart` and `list`, but no way
  to list uploads). `StorageDriver` is a public interface implemented by `r2()`, `s3()` and the fake R2.
- **What goes wrong:** "add a storage call" can only mean a new `StorageDriver` method. That is a public-contract
  change: it needs a decision entry, the fake R2, contract-suite cases and Wrangler (whose ListMultipartUploads
  answers `501`, `docs/research/2026-11-16-m3-slice-measurements.md:118`). None of that is in scope.
- **Fix:** the fixture signs its own requests straight to RustFS, as `storage/s3-driver.rustfs.integration.test.ts:12-27`
  already does with `signRequest` (or with `aws4fetch`, a devDependency):
  - `GET /<bucket>?uploads&prefix=<prefix>`, counting `<Upload>` blocks;
  - `DELETE /<bucket>/<key>?uploadId=` in cleanup.

  Both were measured above to behave as the oracle needs. The library does not change.

### I2. Oracle and cleanup traffic must bypass the proxy, and nothing creates the Node lane's bucket

- **Where:** Task 4: `expectStored` ("read back, SHA-256"), the cleanup, and the smoke row's "the log shows the
  expected sequence".
- **Evidence:** spec §4 says "the object read back through the server's storage". The only S3 endpoint of that storage
  is the proxy (`storage/s3/context.ts:31`, one `bucketUrl`). The `nth` and `"every"` counters count every match
  (plan, Proxy API). A fresh RustFS has no bucket (`scripts/rustfs.sh:9`), and the contract lane creates its own
  (`s3-driver.rustfs.integration.test.ts:12-27`).
- **What goes wrong:**
  - The oracle's `HeadObject`, `GetObject` and `ListObjectsV2` calls are logged as `server` requests. That pollutes
    the log sequence that rows assert, and moves `kind: "server"` counters: a `"every"` rule faults the oracle itself.
  - The first upload fails with `NoSuchBucket` (`STORAGE_ERROR`) unless someone creates the bucket.
- **Fix:** the fixture builds a second `s3()` driver on RustFS's own port (`CLOUDROP_RUSTFS_ENDPOINT`) for read-back,
  listing and cleanup. Its `beforeAll` creates the bucket (409 or 200 is fine) and fails, with a message naming
  `scripts/test-chaos.sh`, when RustFS is unreachable. No CORS rule is needed in the Node lane.

### I3. The soak's file name and gating conflict with the chaos project, and the landed M3-K7 fixes the conflicting name

- **Where:** Task 7 names `src/chaos/soak.chaos.integration.test.ts`, then "prefer … `*.soak.integration.test.ts`",
  then "runs only when `CLOUDROP_CHAOS_SOAK=1`". The file map gives Task 7 only the soak file and `ci.yml`.
  `docs/decisions/m3-chaos.md` M3-K7 "Visible in" (landed in `3ab07a6`) uses `soak.chaos.integration.test.ts`.
- **Evidence:**
  - Task 4's project `chaos` includes `src/**/*.chaos.integration.test.ts`, so that name runs the soak on every pull
    request.
  - A `describe` gated by an environment variable registers no test when the variable is unset, and Vitest fails a
    file with no tests.
  - `*.soak.integration.test.ts` matches `integration`'s `src/**/*.integration.test.ts` (`vitest.config.ts:16`).
  - `.claude/skills/testing-patterns/references/repository.md:31-35` (landed) describes three projects only.
- **Fix:**
  - Name the file `src/chaos/uploads.soak.integration.test.ts`, with no environment gate.
  - Add a Vitest project `soak` (include `src/**/*.soak.integration.test.ts`, a long `testTimeout`) and exclude that
    pattern from `integration`.
  - Root script `test:chaos:soak` runs `scripts/test-chaos.sh soak`; the script picks `--project chaos` or `--project
    soak`.
  - Add `vitest.config.ts`, the root `package.json` and `scripts/test-chaos.sh` to Task 7's files.
  - Correct M3-K7's "Visible in" and the testing skill's lane paragraph in the same task.

### I4. "Reset after N bytes" is undefined for requests without a body, which row 14 needs

- **Where:** Proxy API `{ kind: "reset"; afterBytes }`. Row 14 resets the server's `ListParts` and `HeadObject`.
- **Evidence:** `ListParts` is a GET without a body (`storage/s3/multipart.ts:31-35`), and so is HEAD. A
  `"data"`-counting implementation never fires for them.
- **What goes wrong:** the rule matches, nothing resets, and the request is forwarded or hangs, depending on how the
  executor wrote it.
- **Fix:** define it as "reset when `afterBytes` request-body bytes have been read, or when the body ends, whichever
  comes first, and never forward the answer". Add a Task 1 row: GET with `afterBytes: 0` → `ECONNRESET`, and the
  target got the request or nothing (say which).
- **Also for row 14:** the server sends HEAD in `/complete` only for a single-PUT file (`server/complete.ts:139-141`),
  or for multipart after `NO_SUCH_UPLOAD` (`complete.ts:73-78`). So the HeadObject variant needs a single-PUT file. The
  expected path is fully determined: `transport.ts:93` gives `STORAGE_UNREACHABLE` retryable, then `http.ts:88-91`
  gives `STORAGE_ERROR` retryable with status 502, then the client retries `/complete`, and the file is done. The logger
  received "a storage request failed". Replace "or a documented code" with that path.

### I5. The browser task cannot start the proxy as written: no runner, unknown ports, and a trap that would leak the container

- **Where:** Task 6: "`scripts/test-browser.sh` starts the proxy (with `control: true`) … the control URL reaches
  Playwright through an env variable". The file map has no runner script. The API options are `{ port?, control? }`,
  and the control port is always free-chosen.
- **Evidence:**
  - The proxy is a TypeScript module, and bash can only run it through a script.
  - `CLOUDROP_S3_ENDPOINT` must be exported before `setup:rustfs` and before Playwright's `webServer` builds and starts
    Next, because `examples/next/lib/cloudrop.ts:4` reads it at module load.
  - `scripts/test-browser.sh:23` registers `trap '"$ROOT/scripts/rustfs.sh" down' EXIT`, and a second `trap … EXIT`
    replaces it.
- **Fix:**
  - Add `scripts/chaos-proxy.ts` (runs under Bun or Node; `resetAndDestroy` works in both, measured). It reads
    `CLOUDROP_CHAOS_PROXY_PORT` (default 19110) and `CLOUDROP_CHAOS_CONTROL_PORT` (default 19111) and prints one ready
    line.
  - Add `controlPort?: number` to `startChaosProxy`'s options.
  - In `test-browser.sh`, use one cleanup function that kills the proxy's PID and then runs `rustfs.sh down`. Refuse
    the two ports when busy. Start the proxy after `rustfs.sh up` and poll `GET /log` until ready. Export
    `CLOUDROP_S3_ENDPOINT=http://127.0.0.1:19110` and `CLOUDROP_CHAOS_CONTROL_URL` before `setup:rustfs`.
  - Keep `workers: 1` in `playwright.config.ts`, because the control state is global.
  - Note: the browser tests' own read-back (`storage` from `lib/cloudrop.ts`) now passes through the proxy as a
    `server` request. Rows that fault `server` requests must match by operation, never by `"every"` alone.

### I6. The wave-3 tasks collide on port 19300 and on the shared fixture

- **Where:** File map, wave 3 (5a, 5b, 6 and 7 run in parallel). Global Constraints: "the chaos lane's RustFS uses
  `CLOUDROP_RUSTFS_PORT` default 19300". Tasks 5a, 5b and 7 each run `bun run test:chaos` (three times for stability).
- **Evidence:** Task 4 models the script on `scripts/test-rustfs.sh:7-10`, which exits 1 on a busy port. Rows 1–8 and
  10–14 each need helpers that Task 4's fixture does not list:
  - a single-PUT file versus a multipart file (the default `multipartThreshold` is 64 MiB, `plan.ts:15`);
  - a `Math.random` stub with restore;
  - waiting for a log entry;
  - listing leftover uploads.
- **What goes wrong:** the second and third executors fail on a busy port. If 5a and 5b each add helpers, both edit
  `src/testing/chaos-fixture.ts` and their commits conflict.
- **Fix:** give each wave-3 task its own port (5a 19300, 5b 19310, 7 19320). Make Task 4 deliver every helper listed
  above, and say 5a and 5b do not edit the fixture. A helper found missing later goes through a serialized follow-up.

## Minor

- **M1. Row 2 races the background `/abort`.** `upload()` returns before its background `/abort` lands (S15), so an
  immediate `expectNoUploadsLeft()` is flaky, which matters under "run three times". Wait until the proxy log holds
  `AbortMultipartUpload` with status 204, with a bounded wait, then run the oracle.
- **M2. Rows 2 and 3 depend on file shape.** S12 runs 4 parts at a time, and M3-U18 starts no new part after a failure,
  so a file of more than 4 parts leaves unstarted parts. Then "retry sends only part 2" (row 3) is false. Set
  `multipartThreshold: "8MB"` in the fixture (as `examples/next/lib/cloudrop.ts:28` does) and use 3 parts (20 MiB) for
  rows 1–4 and 7. Use a ≤ 1 MiB single file for rows 5, 6 and 12.
- **M3. `Math.random` is stubbed to 0.** Build the run prefix from `crypto.randomUUID()`, and give the proxy's random
  mode its own seeded PRNG that never calls `Math.random`. Otherwise every run shares prefix `chaos/0…/` and the soak
  loses its randomness.
- **M4. The proxy must not touch request headers.** State that it forwards every request header verbatim and adds
  none: SigV4 signs `host`, `x-amz-date`, `x-amz-content-sha256` and, for presigned PUTs, `content-length`
  (`storage/s3/presign.ts:36`). No `x-forwarded-*`, and no change to `content-length` or `transfer-encoding`. An
  `answer` fault drains the request body before it answers, so `bytesIn` is meaningful and XHR is never reset
  mid-upload. Node fetch copes either way (measured); Chromium was not measured.
- **M5. `stop()` cannot be checked as Task 1 says.** Task 1 checks `server.listening === false`, but `ChaosProxy`
  exposes no server. Assert `ECONNREFUSED` on `url` and `controlUrl` instead.
- **M6. The log cannot say the client gave up.** `ChaosEntry.outcome` has no value for "the client closed the
  connection" (a fetch timeout in row 10, an XHR abort in rows 15 and 16). Add `"aborted"`, and say what a black-holed
  entry becomes after the client leaves.
- **M7. The `cors` default is unstated.** The API's `answer.cors?` default is unspecified, while Task 6 says
  synthesized answers carry CORS "unless the row says not". Make the default "echo `Origin` when the request has one".
  Also say whether a black hole forwards the request upstream.
- **M8. Spec and plan name the control calls differently.** Spec §2's in-process control is `set(rules)`, `clear()`,
  `log()` and `stop()`. The plan has `clearLog()`, `random()` and `release()`. Align the spec, since it is called
  binding.
- **M9. The soak needs replay and clean final aborts.**
  - Read the seed from `CLOUDROP_CHAOS_SEED`, falling back to a random one, so a printed seed can be replayed.
  - Allow `workflow_dispatch` on `chaos-soak`, and give both new jobs a `timeout-minutes`.
  - Turn random faults off before the final `abort()` of failed files and before the oracle, or a faulted `/abort`
    leaves uploads behind.
  - Apply C3's M3-U55 exception.
- **M10. Rows 5 and 4 can be exact.** In row 5 the injected 503 is never forwarded, so the retry gets 200, never 412;
  drop the "may answer 412" hedge. In row 4, measure the gap from the first attempt's `endMs` to the second's
  `startMs`. In the browser's not-exposed variant, assert gap < 2000 ms, since jitter's first ceiling is 0.5 s
  (`client/retry.ts:14-15`).
- **M11. Fallback home for the stall row.** If the `page.clock` spike fails, M3-K3 sends "one real-time stall row" to
  the nightly job. But no nightly browser job exists, and Task 7 adds only the Node `chaos-soak` job. Name the home: a
  Node fetch-transport row in the `soak` project (single PUT ≤ 64 KiB, about 30.6 s), or a nightly browser job.
- **M12. Unit-lane budget for the proxy tests.** `chaos-proxy.test.ts` runs in the unit lane, which must stay ≤ 5 s
  cold (testing-patterns SKILL.md:88). Keep throttle and delay rows to kilobytes and tens of milliseconds.
- **M13. Shared worktree.** If wave-3 tasks share one worktree, `bun run verify` (Biome, typecheck) sees each other's
  unfinished files. Give each parallel task its own worktree under `~/projects/.worktrees/cloudrop/`.

## Checks that passed

- **Labels.** The s3 driver always uses path-style URLs (`storage/s3/context.ts:31`, `objectUrl` `:36-40`). Every
  operation can be told apart by method plus query names:
  - `uploads` on a key (POST) is CreateMultipartUpload; on the bucket (GET) it is ListMultipartUploads;
  - `uploadId` with GET is ListParts, with POST CompleteMultipartUpload, with DELETE AbortMultipartUpload;
  - `partNumber` is UploadPart;
  - `list-type=2` is ListObjectsV2 (`objects.ts:156`);
  - `?cors` and `?lifecycle` are "Other".

  Sources: `storage/s3/multipart.ts:34,54,95,111` and `objects.ts:156`.
- **Presigned versus server.** Presigned PUTs carry their signature in the query (`presign.ts:33-43`). Server calls
  carry an `Authorization` header (`transport.ts:71-80`). There is one `endpoint` and an optional `fetch`
  (`presets.ts:25-36`), so the proxy must be the endpoint, as planned.
- **Node 24 and Bun.** `resetAndDestroy` is available in both, and the client sees `ECONNRESET` (measured).
- **RustFS behaviour the oracle needs.** ListMultipartUploads by prefix reads 0 after complete and after abort, and
  `If-None-Match: *` gives 412 (measured). The contract's `finishedUploadsLinger` gap does not show up in
  ListMultipartUploads.
- **Row 4 (Node).** Node fetch reads `Retry-After` on a synthesized 429. `retryDelay` returns
  `max(retryAfter, 0)` with `Math.random` at 0 (`retry.ts:13-16`), so the ≥ 2000 ms gap holds, and a 429 is not
  renewed (`bucket.ts:41`).
- **Rows 6–8.** `bucket.ts:33-43`: `SignatureDoesNotMatch` is rejected, `AccessDenied` and `ExpiredRequest` are renewed
  once, and 500 is retried up to 6 attempts (`retry.ts:7`).
- **Row 13.** The storage's 503 becomes `RATE_LIMITED` (`storage-error.ts:65-69`), then a retryable 503 to the client
  (`http.ts:83-87`), and the client retries `/complete`. The injected Complete never reaches RustFS, so the linger gap
  does not matter.
- **No hidden traffic.** Vitest sets `NODE_ENV=test`, so the development bucket check (`handler.ts:145`) adds no
  storage calls to the log.
- **Vitest wiring.** `unit` already excludes `*.integration.test.ts` (`vitest.config.ts:10`). Excluding
  `*.chaos.integration.test.ts` from `integration`, as Task 4 plans, separates the chaos files. A loopback `node:http`
  server in the unit lane has precedent (`src/node.test.ts`). The `tsconfig.json` exclusion follows `page-events.ts`
  (`tsconfig.json:21-27`).
- **Lane script.** It can copy `test-rustfs.sh`: trap first, a unique `$$` container name, the `cloudrop.test` label
  from `rustfs.sh:9`, a busy-port refusal. Port 19300 was free on this machine.
- **CI.** Pinned action SHAs exist to copy (`ci.yml:28-36`). `rustfs/rustfs:1.0.5` already runs on `ubuntu-latest`
  (jobs `rustfs`, `browser`). `bunx vitest` runs Vitest under the `setup-node` Node 24.
- **Browser endpoint switch.** The example reads `CLOUDROP_S3_ENDPOINT` at module load (`examples/next/lib/cloudrop.ts:4`),
  so pointing it at the proxy reroutes the server's calls, the presigned URLs and the test's read-back together. The
  RustFS CORS rule names origins only (`setup-rustfs.ts:7-8`), so the change of bucket host is harmless.
- **Already landed.** Tasks 2 and 3 match the plan. The R2 `Retry-After: 5` claim has evidence
  (`docs/research/r2-spike-findings.md:612`).
- **Wave 1.** Tasks 1, 2 and 3 edit disjoint files; only Task 2 uses port 5173.
- **Runtime budget.** With jitter at 0 and C2 fixed, the Node lane's waits are row 4's 2 s, plus row 10's 30.6 s if
  it stays in Node, plus 16 s for row 11. Loopback transfers of 20 MiB files take well under a second. That fits the
  60–90 s budget, given per-test timeouts ≥ 45 s for rows 10 and 11.
