# Plan audit: M3 resume after reload

Plan `docs/superpowers/plans/2026-11-16-m3-resume.md` (head 57144e0), spec `docs/superpowers/specs/2026-11-16-resume-design.md`.
Paths below are relative to `packages/cloudrop/src/` unless they start with `docs/` or `examples/`. Read-only audit:
nothing was run except reading files and one `node -e` probe of Node 24's globals.

Counts: **Critical 2 · Important 12 · Minor 14**.

## Critical

### C1. An async fingerprint breaks R2's ordering: a cancelled or fast file keeps its record (with its token)

- **Plan:** R2 (line 50), Task 1 `Records.save(record: UploadRecord)` (line 105), Task 4 "save when a multipart ticket
  arrives" (line 215). The plan never says where the fingerprint is computed. Spec §3.2 says "a delete issued after a
  save never runs before it".
- **Evidence:** `fingerprintOf` returns a `Promise<string>` (plan line 162). The record needs it (`fingerprint: string`,
  line 100), so the only way to call `save` with the plan's interface is `fingerprintOf(file).then(fp => records.save(…))`.
  The removes are synchronous calls from `file-run.ts`: `runFile`'s done branch (`client/file-run.ts:185-188`), `end()`
  (`:145-163`), `abortFile` (`:132-142`). A job cancelled during `/upload` gets its ticket in `runEntry`
  (`client/job-run.ts:100-106`). `runFile` then skips the loop and runs `end(aborted)` in the same tick (`file-run.ts:173,194`).
  So `remove(id)` is queued **before** the save, which is still waiting for the hash.
- **What goes wrong:** the save runs after the remove. A cancelled upload (and any file that settles before its hash
  resolves) leaves a record holding a live token for 24 h. That breaks the owner's security limit in spec §4 ("the record
  is deleted the moment its file ends done or aborted"). `resumable()` then lists an upload that was aborted or is done.
  The same race brings a record back after `forget()`, which breaks sign-out.
- **Fix:** let the queue hold the slot when the call is made. Change `save` to accept `UploadRecord | Promise<UploadRecord | null>`
  and have the queue `await` it inside the chain (a `null` or a rejection skips the write). Task 4 starts
  `fingerprintOf(file)` in `runEntry` when the ticket is multipart and the store is enabled, and calls
  `records.save(fpPromise.then(build))` synchronously. Do not hash when persistence is off. Add a Task 4 row: "job aborted
  while `/upload` is in flight, ticket arrives → `fake.stored()` empty after the queue drains". Add a Task 1 row: "save of
  a pending promise, then remove, issued synchronously → nothing stored". Task 1 is in flight, so this is a small
  `records.ts` change in Task 4.

### C2. A failed file that keeps its ticket does not hold the lock, so resume() can complete it and the old entry's /abort then deletes the finished object

- **Plan:** R4 (lines 54-55: "held until the file's run settles (done, failed or aborted)"); spec §3.5 ("from its first
  request to its settling"); Task 6 lab "Unfinished uploads" from `resumable()` (line 276). Spec §3.2 keeps a failed
  file's record.
- **Evidence:** a failed file of `start()` keeps its upload and is held for pagehide (`file-run.ts:148-152`,
  `client/lifecycle.ts:124-133`). `abortFile` of a failed file sends `/abort` (`file-run.ts:139-141`), and so does the
  job's signal (`job-run.ts:47-50`). `/abort` with an unexpired token deletes this upload's object even when it was
  completed (`server/abort.ts:24-32`).
- **What goes wrong (same tab or another tab):**
  1. A file fails and keeps its ticket; its run settles, so R4 releases the lock.
  2. The page lists it (`resumable()` returns failed files' records by design). The user picks Resume, and the lock is
     free, so the probe completes the upload and removes the record.
  3. The old entry still holds the same token. When the tab closes, pagehide sends `/abort`, which **deletes the
     completed file**. The same happens when the user clicks cancel on the old failed row, or when the old job's signal
     fires.

  This is data loss after success was reported. Two concurrent `retry()`/`resume()` runs of one upload are also possible.
- **Fix:** hold the lock for as long as an entry keeps the ticket alive, not for one run. Take it when the ticket arrives,
  or in `resume()` (R7). Release it when the entry gives the upload up: done; aborted; `/abort` sent (`drop()`, the
  pagehide handler); a new ticket replacing it (`requeue(fresh)`, R5); or the page unloading (automatic).
  `lockUpload(id, until)` already allows this: `until` is a per-`Upload` deferred. Record it as an execution ruling that
  amends R4 and spec §3.5's wording; the intent, one holder per upload, is unchanged. Have `UPLOAD_IN_USE`'s message cover
  "this page" too (M4). Rows:
  - unit: a failed file kept, then `resume()` of its record in the same client → `UPLOAD_IN_USE` and no request;
  - unit: after `abort()` of the failed file → `resume()` gets `NOT_FOUND`, because the record is gone;
  - browser: two pages, the first holding a failed file → the second gets `UPLOAD_IN_USE`.

## Important

### I1. R5 ("start over without settling") needs file-run.ts and a resume-specific first run, which Task 5 does not name

- **Plan:** R5 (lines 56-58); Task 5 files (lines 239-243) name `upload.ts`, `job-run.ts`/`job.ts` but not `file-run.ts`.
- **Evidence:** every error that reaches `runFile` calls `end()` (`file-run.ts:192`). `end()` settles `failed`, holds
  leftovers (`:148-152`), publishes, and sets `firstOutcome` (`:87-90`). That is exactly what R5 forbids. `firstRun`
  captures `entry.run` once (`job-run.ts:146-147`) and casts `firstOutcome` (`:150`). A run reassigned by a start-over
  `launch()` (`:121`) is not awaited, so `done` would resolve with a `null` outcome, a TypeError path.
- **Fix:** specify the mechanism:
  - `Upload` gains `probe: boolean`, true for a rebuilt upload.
  - In `runFile`, before `end()`, when `upload.probe` is set, the file is not cancelled, and the code is in
    `{UPLOAD_EXPIRED, INVALID_TOKEN, NO_SUCH_UPLOAD}`, return a "start over" marker without settling.
  - The resume job's first run then does `requeue(job, entry, true)` (which removes the old record and releases leftovers
    and the lock), publishes `queued` with bytes 0 (M3-U36), and runs `await launch(job, [entry])`. `done` waits for that
    final run. Do not reuse `firstRun`; write `resumeRun(job)`.
  - State what a refused new `/upload` gives. With `launch`'s `whole === true` (`job-run.ts:119`) it is
    `{ data: null, error }`, the error unwrapped by `withFile`, as a refused `start()`. Spec §2.1 says "the job's normal
    UploadResult", so either fits; pick one and test it.
  - Add rows: `abort()` between the probe's answer and the new ticket → aborted, `/abort` with the new token only, no
    record left; and a refused new `/upload`.

### I2. resume()'s lock check and the run's lock are two acquisitions, and Web Locks do not re-enter

- **Plan:** R7 (lock as the last validation step, lines 61-62), Task 4 "lock around the run" in `job-run.ts` (line 215),
  Task 2 `lockUpload(id, until)` (line 168).
- **Evidence:** if `resume.ts` takes the lock to validate and `runUpload` (`job-run.ts:67-74`, the shared entry point of
  first runs and retries) takes it again with `ifAvailable`, the second request finds the lock held by the same page.
  Web Locks have no re-entrance, so every resume would end `UPLOAD_IN_USE` against itself. The plan also never says what
  a `start()`/`retry()` run does when `lockUpload` returns false.
- **Fix:** one acquisition per held ticket, as in C2. The holder sits on the `Upload` (for example `upload.release`). The
  run only takes the lock when the `Upload` holds none, which happens on a fresh ticket. `resume()` takes it and hands it
  to the rebuilt `Upload`. A refusal in a retry's run settles `failed` with `UPLOAD_IN_USE` (`withFile`) and sends nothing.

### I3. R6 covers only the PARTS_MISSING answer: a probe that succeeds reports a done file with bytes 0

- **Plan:** R6 (lines 59-60), Task 5 row 4 (lines 255-256).
- **Evidence:** bytes come only from `progress.sent` during PUTs (`client/upload.ts:84`, `client/progress.ts`). The
  snapshot relies on "done means bytes = size" (`client/job-snapshot.ts:15-18`). A probe answered with success
  (`upload.ts:143-145`) never sends a byte, so the resumed done file shows `bytes: 0`, `progress: 0`, and the job's totals
  stay below 1.
- **Fix:** when the probe gets its first answer that is success or `PARTS_MISSING`, credit
  `entry.progress.sent(n, size, size)` for each part still in `landed`. Use neither `pool.sent` nor `meter`: no bytes
  flowed. Then clear `probe`.
  - Define when the probe flag is set again: a `retry()` whose probe never got either answer probes again (spec §3.4:
    "start again from the probe").
  - `requeue` resets `repairs` to 0 (`client/retry-file.ts:40`). Either keep a separate flag, or model the free round as
    `repairs: -1` on a rebuilt upload and have `requeue` restore -1 while `probe` is still set.
  - Rows: probe success → snapshot `bytes === size`; probe NETWORK_ERROR ×6 → failed, then `retry()` → the next
    `PARTS_MISSING` is still free.

### I4. Adding NO_SUCH_UPLOAD to NEEDS_NEW_TICKET does nothing after a /complete that left doubt

- **Plan:** R5 last sentence (line 58), Task 4 row 4 (lines 228-229), spec §3.4.
- **Evidence:** `needsTicket` returns false whenever `mayBeComplete` is set (`retry-file.ts:26`), before it reads the code
  list (`:27`). `mayBeComplete` is sticky for every code except PARTS_MISSING (`upload.ts:131-133`). NO_SUCH_UPLOAD is
  what `/complete` answers once HEAD has shown that this upload's object does **not** exist (`server/complete.ts:72-77`).
  So it settles the doubt just as PARTS_MISSING does (ruling S-9). After a probe that got NETWORK_ERROR and then
  NO_SUCH_UPLOAD, every `retry()` reuses the dead ticket and fails NO_SUCH_UPLOAD again, with no way out.
- **Fix:** in `complete()` (`upload.ts:131`), clear `mayBeComplete` on NO_SUCH_UPLOAD as well as PARTS_MISSING, and
  record that as an execution ruling citing `server/complete.ts:72-77`. Add a row: `/complete` NETWORK_ERROR, then
  NO_SUCH_UPLOAD → failed; `retry()` → `POST /upload`, a new key.

### I5. Where records are removed: the plan's list misses paths that send /abort

- **Plan:** Task 4 "`file-run.ts` (remove on done and aborted)", "`lifecycle.ts` (pagehide's `/abort`…)" (lines
  216-217); spec §3.2.
- **Evidence:** `upload()` runs with `keepFailed: false` (`client.ts:154`). Its failed file goes through `end()` to
  `drop()`, which sends `/abort` (`file-run.ts:155-162`). It ends `failed`, not `aborted`, so "remove on done and
  aborted" leaves the record pointing at an aborted upload. Spec §3.2 also names only `start()`, `resume()` and `retry()`
  as writers and never says whether `upload()` persists.
- **Fix:** state that `upload()` persists, since it is built on `startJob` and needs it as much, and list every hook
  point:
  - `runFile` done (`file-run.ts:185-188`);
  - `drop()` (`:122-125`), which covers `end()`'s cancel, `upload()`'s failure, and `abortFile` of a failed file;
  - `end()` aborted with `mayBeComplete` (`:155-158`, no `drop`);
  - `abortFile` of a failed file with `mayBeComplete` (`:139-141`);
  - the pagehide loop (`lifecycle.ts:125-130`);
  - `requeue(fresh)` for the old id (`retry-file.ts:34-37`);
  - R5's start-over.

  A failed file with `mayBeComplete` keeps its record in `upload()` as in `start()`. Add rows for `upload()` failing
  without doubt (record removed) and with doubt (record kept).

### I6. Task 5 row 2's expected request sequence leaves out /sign

- **Plan:** line 250: "`POST /complete`, then exactly `PUT part 3`, `PUT part 4`, `POST /complete`".
- **Evidence:** a rebuilt ticket has `parts: []` (spec §5), so `senderFor`'s `first` is empty (`upload.ts:100-106`).
  `urlFor` then signs through `signAhead` before any PUT (`client/parts.ts:224-233`, `:211-222`).
- **Fix:** the sequence is `POST /complete`, `POST /sign`, `PUT part 3`, `PUT part 4`, `POST /complete`. Assert the
  parts asked for in the `/sign` body, `[3, 4]`, because that is the oracle for "only the missing parts". Task 6 row 1's
  "only the missing parts" also has a `/sign` line in the table.

### I7. What a resume job looks like while it validates asynchronously is unspecified

- **Plan:** R7 (lines 61-62), Task 5 (lines 242-243), spec §2.1 ("`done` resolves `{ data: null, error }` without any
  request").
- **Evidence:** `startJob` builds entries and handles synchronously (`client/job.ts:187-213`). An argument error gives
  `files: []`. The record lookup, the hash and the lock in `resume()` are all async, and the plan says nothing about:
  - the file's status before validation ends (the plan says "starts as `completing`");
  - `files`/`getSnapshot` when validation fails asynchronously;
  - `abort()`, `pause()` or an already-aborted `signal` during validation;
  - when `nextRank()` is called (spec §2: "the client's next sequence number").
- **Fix:**
  - Call `nextRank()` synchronously in `resume()`.
  - Bad arguments (synchronous) are handled like `startJob`'s: `files: []`.
  - Otherwise there is one entry, `queued`, until validation passes, then `completing`.
  - A failure settles it `failed` with the bare error (as a whole-job refusal) and `done` gives `{ data: null, error }`.
  - `abort()` or the signal during validation → `ABORTED`, no request, record untouched.
  - Add those rows.

### I8. The tests have no way to wait for the store before reading fake.stored()

- **Plan:** Task 4 oracle "`fake.stored()`" (line 220), Task 1 fake events "a microtask or `setTimeout(0)`" (line 131).
- **Evidence:** `Records.save`/`remove` return `void` (lines 105-106). In Task 4, `client.resumable()` does not exist yet,
  so there is no queued read to use as a barrier, and `await job.done` says nothing about the IndexedDB queue. Most
  client tests fake only `Date` (`client/retry-file.test.ts:131`, `client/upload.test.ts:245`), but those that fake timers
  would block a fake that uses `setTimeout(0)`.
- **Fix:** `FakeIndexedDb` gains `settled(): Promise<void>`, which resolves once no request or transaction is pending
  (looping until quiet). The fake fires events with `queueMicrotask` only (Vitest does not fake it by default). Tests do
  `await job.done; await fake.settled(); expect(fake.stored())…`. With C1, `settled()` must also cover a pending hash, so
  have it wait on the client queue's tail. A test-only `records.idle()` reached through the fixture works too.

### I9. Task 5's reload simulation as written keeps the first client's lock, or finishes the upload

- **Plan:** Task 5 row 2 "stop the first client by aborting its PUTs without `abort()`… drop the job" (lines 248-249);
  row 3 "the first client's `/complete` answered but dropped" (lines 253-254).
- **Evidence:**
  - Hung PUTs keep the first run unsettled, so its lock stays held (`FakeLocks` has no "page gone" release, line 170),
    and the second client's `resume()` ends `UPLOAD_IN_USE`.
  - A dropped `/complete` is NETWORK_ERROR, which is retryable, so `withRetry` sends it again (`client/retry.ts:56-63`,
    `upload.ts:143`). The second `/complete` finishes through `completedBefore` (`server/complete.ts:72-75`), and the
    file ends done with its record removed before the "reload".
- **Fix:**
  - Either `FakeLocks` gains `releaseAll()` (a page unload), or the interruption is a non-retryable fault on PUT 3/4
    (403 `AccessDenied` → `failed`, record kept, run settled). With C2's longer hold, a failed entry still holds the lock,
    so `releaseAll()` is the right tool.
  - Row 3 forwards every first-client `/complete` and throws on each answer (six attempts → `failed`, `mayBeComplete`,
    record kept). Then the second client's probe sends one `/complete`, ending done with the same key.
  - Both clients share one `clientFixture` (one server, one fake bucket, one set of token keys); separate fixtures would
    not share the bucket.

### I10. Browser rows 1 and 2 cannot run reliably with the lab's current faults

- **Plan:** Task 6 rows (1) and (2) (lines 280-283).
- **Evidence:**
  - Row 2: `dropComplete` is one-shot, and its text says "The client sends /complete again"
    (`examples/next/app/lab/fault-panel.tsx:29-32`). The retry waits a full-jitter delay of at most 500 ms

    is held.
  - Row 1: run at `concurrency: 1` (a lab option, `examples/next/app/lab/page.tsx:90`) with the delay fault, and wait
    for the table's "PUT part 1 stored" before `page.reload()`.
  - Create the on-disk file once, with deterministic bytes, under the test's output directory in the worktree (not
    `/tmp`), so `lastModified` stays stable across the reload.

### I12. Store calls that throw synchronously, and metadata that structured clone refuses

- **Plan:** Task 1 rows 6-7 (only asynchronous `failNext`), spec §3.2 ("a store error never fails… an upload").
- **Evidence:**
  - `objectStore.put` throws `DataCloneError` synchronously for values JSON accepts but structured clone refuses (a
    function-valued property; `readArguments` checks only `JSON.stringify`, `client/arguments.ts:17-24,53`).
  - `db.transaction` throws `InvalidStateError` once the browser closes the connection (clear site data, eviction).
  - `indexedDB.open` throws `SecurityError` in opaque-origin iframes.

  None of these is an async `onerror`.
- **Fix:** store `metadata` as `JSON.parse(JSON.stringify(metadata))`, which is also exactly what `/upload` received.
  Wrap every store call, open included, in `try`. On `InvalidStateError` or the connection's `close` event, drop the
  cached database so the next call reopens it. That amends R2's "a failed open makes every later operation fail": once
  per call is enough. Add fake knobs `throwNext(name)` (synchronous) and `closeConnection()`, and rows: metadata
  `{ f() {} }` → the upload completes, no record, no unhandled rejection; a closed connection → the next save works.

## What /complete really answers (point 4)

| Case | Answer | Where |
|---|---|---|
| parts missing or the wrong size | `PARTS_MISSING` 409 with `parts` | `server/complete.ts:88-101`, `server/http.ts:37` |
| multipart gone, own object at the key with the token's size | **success** (afterVerify and onComplete run again) | `complete.ts:82-86,72-75` then `:158-185` |
| multipart gone, no own object | `NO_SUCH_UPLOAD` 410, not retryable | `complete.ts:76`, `http.ts:20` |
| completion raced with NoSuchUpload | the same HEAD path | `complete.ts:107` |
| expired token | `UPLOAD_EXPIRED` 410 | `token.ts:118`, via `token-request.ts:146` |
| bad signature, format or length | `INVALID_TOKEN` 400 | `token.ts:112-117` |
