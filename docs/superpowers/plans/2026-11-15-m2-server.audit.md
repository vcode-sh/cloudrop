## Task 1: Error codes, shared configuration helpers and the protocol types

### T1-1 Important: `Jsonified` is wrong for `undefined`, `unknown`, numeric keys and `void`

Plan lines 642 to 655 (`Jsonified`), 3137 to 3141 (`CompleteContext`) and 3189 to 3191 (`route()` return type).

What is wrong (all measured with `tsc` 7.0.2):

- `Jsonified<undefined>` is `never`. A route without a schema types `onComplete`'s `metadata` as `never`, so
  `metadata.anything` compiles. At runtime it is `undefined`.
- `unknown extends …` falls through to `never`, so `Jsonified<{ a: unknown }>` drops `a`. An authorize result with an
  `unknown` field loses it in `onComplete`.
- `K extends string` drops numeric keys, which JSON keeps (`{ 1: "x" }` becomes `{"1":"x"}`).
- An `onComplete` that returns nothing gives `RouteResult` `never`; the wire carries `data: null` (`complete.ts`
  maps `undefined` to `null`).

The plan's type test never tries any of these.

Replacement. In `src/protocol/types.ts`, replace the whole `Jsonified` declaration with:

```ts
/** What a value becomes after JSON.stringify and JSON.parse: Dates turn into strings, functions and undefined vanish. */
export type Jsonified<T> = unknown extends T
  ? unknown
  : T extends { toJSON(): infer J }
    ? Jsonified<J>
    : T extends string | number | boolean | null
      ? T
      : T extends undefined | symbol | bigint | ((...args: never[]) => unknown)
        ? never
        : T extends readonly (infer E)[]
          ? Jsonified<E>[]
          : T extends object
            ? {
                [K in keyof T as K extends string | number
                  ? Jsonified<T[K]> extends never
                    ? never
                    : K
                  : never]: Jsonified<T[K]>;
              }
            : never;
```

In `src/server/route.ts` (Task 7), replace `CompleteContext` with:

```ts
/** `onComplete` runs inside `/complete`, so it sees what the token carried: the JSON form of each value. */
export type CompleteContext<TAuth, TMetadata> = Omit<Jsonified<TAuth>, ReservedName> & {
  request: Request;
  file: UploadedFile;
  /** undefined on a route without a schema. */
  metadata: [TMetadata] extends [undefined] ? undefined : Jsonified<TMetadata>;
};
```

In the same file, replace the `route()` signature's return type with:

```ts
): Route<
  SchemaInput<TSchema>,
  [Awaited<TResult>] extends [undefined | void] ? null : Jsonified<Awaited<TResult>>
> {
```

Add to `src/protocol/types.test.ts`, inside `describe("Jsonified", …)`:

```ts
  it("keeps unknown values and numeric keys, as JSON does", () => {
    expectTypeOf<Jsonified<{ a: unknown; 1: string }>>().toEqualTypeOf<{ a: unknown; 1: string }>();
  });
```

Add to `src/server/types.test.ts` (Task 12), inside `describe("type inference for the client", …)`:


## Task 2: Size strings and the accept policy

### T2-1 Minor: an unknown type keeps an extension that names a known type

Plan line 1011. `matchAccept(["*/*"], "application/octet-stream", "payload.html")` gives `{ ext: ".html" }`, so the key
ends in `.html`. The stored type and the `attachment` disposition keep this safe on R2, but a key that claims HTML is
misleading to every tool that keys on the extension (CDN rules, downloads, antivirus). Dropping the extension is safer
than refusing the file: browsers send `""` for many real files, and those become `application/octet-stream`.

Replacement for that line in `src/server/accept.ts`. Add this above `MIME_TYPE`:

```ts
/** Extensions of the known types: a file declared as another type never carries one into its key. */
const KNOWN_EXTENSIONS: ReadonlySet<string> = new Set(Object.values(EXTENSIONS).flat());
```

Then replace the `if (known === undefined) return …` line with:

```ts
  if (known === undefined) {
    const plain = ext !== null && /^[a-z0-9]{1,16}$/.test(ext) && !KNOWN_EXTENSIONS.has(ext);
    return { ext: plain ? `.${ext}` : "" };
  }
```

Add to `accept.test.ts`:

```ts
  it("keeps the extension of a known type out of the key of a file declared as something else", () => {
    expect(matchAccept(["*/*"], "application/octet-stream", "payload.html")).toEqual({ ext: "" });

```

## Task 3: The upload token

### T3-1 Important: the 8,192-character cap refuses tokens that `/upload` itself issues

Plan lines 1247 and 1248, D2 (line 80) and the Global constraints (line 58).

What is wrong: owner and metadata may each be 2,048 bytes of JSON, a key 1,024 bytes, and a name 255 code points. A
control character costs 6 JSON bytes (`\u0001`); the name check (line 4840) refuses neither control characters nor
emoji. Measured with the plan's payload shape: both caps reached, a 1,024-byte key and 255 control characters give a
9,111-character token. Both caps reached, a 255-character CJK name, a 120-byte key and a 200-character upload ID give
7,195 characters. `/upload` then returns a token that `/sign`, `/complete` and `/abort` all refuse as `INVALID_TOKEN`
("Start the upload again"). The client restarts, gets the same oversized token, and loops.

Replacement in `src/server/token.ts`:

```ts
// The longest token /upload issues: 2 KiB of JSON each for owner and metadata, a 1,024-byte key, a 255-character name
// (up to 6 JSON bytes per character) and the storage's upload ID come to about 12 KiB of base64url. A longer one is
// refused before any HMAC; the 64 KiB body cap still bounds the request.
const MAX_TOKEN_LENGTH = 16_384;
```

Update D2 and line 58 to say "tokens longer than 16,384 characters are refused before any HMAC". The tests are in
T3-2.

Plan line 1187. `${"a".repeat(8192)}.${"b".repeat(43)}` fails the HMAC whether or not the cap exists, so deleting the

## Task 5: Standard Schema metadata

### T5-1 Important: the issue path is echoed unbounded, with line breaks, to the client and the log

Plan lines 1796 to 1801, and D28 (line 160). Only `issue.message` is cut to 200 characters. The path is appended
whole, and a path is often client data: with `z.record(z.string(), z.number())`, the failing key is the client's own
JSON key, up to 64 KiB, newlines included. It is reflected in the response and lands in any log of the message. The
same holds for messages that quote the received value.

Replacement in `src/server/schema.ts`:

```ts
/**
 * The first issue for the client: the message with its path, cut to 200 characters. Both can echo the client's own
 * input (a record key, a received value), so line breaks and other control characters become spaces.
 */
function describeIssue(issue: StandardIssue): string {
  const path = (issue.path ?? []).map((segment) => String(typeof segment === "object" ? segment.key : segment));
  const text = path.length > 0 ? `${String(issue.message)} (at ${path.join(".")})` : String(issue.message);
  return Array.from(text, (char) => {
    const code = char.codePointAt(0) ?? 0;
    return code < 0x20 || (code >= 0x7f && code <= 0x9f) ? " " : char;
  })
    .slice(0, 200)
    .join("");
}
```

Add to `schema.test.ts`:


## Task 7: Routes, the plugin contract and configuration checks

### T7-1 Important: refusals that are not recognised fail open

Plan lines 3100 to 3114 (`DENIED`, `isUnauthorized`) and 4964 to 4968 (`upload.ts`).

What is wrong:

1. `DENIED` is `Symbol("cloudrop.unauthorized")`, private to one module instance. An app that loads two copies of
   cloudrop (two versions in a monorepo, or a helper package with its own copy) calls `unauthorized()` from one copy,
   and the other does not recognise it. `{ message }` is an object, so it passes the `typeof` check, and the upload is
   signed with `owner: { message: "…" }`.
2. Every object passes that check. A Next.js habit, `return new Response(null, { status: 401 })`, or
   `return new Error("…")`, authorizes the upload, and `TAuth extends object` type-checks both.

Replacement in `src/server/route.ts` (Task 7):

```ts
// Symbol.for, not Symbol(): two copies of cloudrop in one app must recognise each other's refusals, or one would read
// as a signed-in user.
const DENIED: unique symbol = Symbol.for("cloudrop.unauthorized");
```

Replacement in `src/server/upload.ts` (Task 8), for the `typeof auth` check:

```ts
  // Only a plain object authorizes: a Response or an Error is an object too, and reading one as the user would sign
  // uploads for a refused request.
  if (typeof auth !== "object" || auth === null || ![Object.prototype, null].includes(Object.getPrototypeOf(auth))) {
    throw new TypeError(`Route "${route.name}": authorize must return a plain object or unauthorized().`);
```


### T8-3 Minor: D14 as a security trade-off, plus one cheap defence in depth

Plan lines 4643 to 4657, and D14.

D14 is safe as designed. Every browser sends `Origin` on a cross-site POST. A form post (`text/plain`, urlencoded,
multipart) gets 415 before any work. A `no-cors` fetch cannot set `application/json`, and a CORS fetch preflights. A
request without `Origin` therefore carries no victim cookies a browser attached cross-site.

The one gap is a browser or extension that strips `Origin`. Such a browser still sends `Sec-Fetch-Site`, so refusing
`Sec-Fetch-Site: cross-site` without `Origin` closes it for free. Replacement at the top of `checkOrigin`:

```ts
  const origin = request.headers.get("origin");
  if (origin === null) {
    // A browser that strips Origin still sends Sec-Fetch-Site; servers and native apps send neither.
    return request.headers.get("sec-fetch-site") === "cross-site" ? { allowed: false } : { allowed: true, cors: {} };
  }
  if (origin === new URL(request.url).origin) return { allowed: true, cors: {} };
```

Add to `describe("cloudrop.handler origins and CORS", …)`:

```ts
  it("refuses a request without Origin that the browser marks as cross-site", async () => {
    const fixture = setup();
    const response = await fixture.cloudrop.handler(
      request("/api/cloudrop/upload", { headers: { "sec-fetch-site": "cross-site" } }),
    );
    expect(await outcome(response)).toEqual({ status: 403, code: "ORIGIN_NOT_ALLOWED" });
  });
```

Update D14 and the spec §7.2 edit (Task 17 edit 5) to name `Sec-Fetch-Site`.

## Task 10: POST /abort

### T10-1 Critical: an expired token deletes a completed file, forever

Plan lines 5774 to 5793, D20 (lines 133 to 135) and the "Not settled" note (line 8668).

What is wrong: `/abort` verifies with `allowExpired: true`, then deletes the single-PUT object whenever its
`cloudrop-id` matches. Nothing distinguishes an upload that never finished from one that `/complete` accepted and the
app recorded through `onComplete`. D20 claims the window is 24 hours, but the code puts no time limit on it.

Anyone who holds a token, even years later, can delete the file with no authorization (D4), and the app is not told:
`onAbort` is a plugin hook, not a route callback. The token is readable by the browser and persisted by the M3 client
(§6.3). Plausible abuse:

- A removed team member deletes files they uploaded to the team.
- A user deletes evidence an app keeps for moderation.
- Any leaked token is a permanent delete capability.

Replacement: the whole of `src/server/abort.ts` (this also fixes T10-2):

```ts
// POST /abort (spec §5.5): the user cancelled. An expired token still aborts what never finished, but never deletes a
// stored file: /abort keeps no state and cannot tell an upload that landed from one /complete accepted.

import { fail, ok, type Result } from "../errors.ts";
import type { AbortResponse } from "../protocol/types.ts";
import type { EndpointInput } from "./config.ts";
import { storageFailure } from "./http.ts";
import { runOnAbort } from "./plugins.ts";
import { nowSeconds } from "./presign.ts";
import { isMultipart } from "./token.ts";
import { abortContext, readTokenRequest } from "./token-request.ts";

export async function handleAbort({ body, config }: EndpointInput): Promise<Result<AbortResponse>> {
  const verified = await readTokenRequest(body, config, { allowExpired: true });
  if (verified.error) return verified;
  const { token } = verified.data;
  const { storage, logger } = config;
  if (isMultipart(token)) {
    const aborted = await storage.abortMultipart(token.key, token.uploadId);
    if (aborted.error) return fail(storageFailure(aborted.error, logger));
  }
  // A single PUT may have landed, and a multipart upload may have completed: this upload's own object (never another
  // writer's) is deleted while the token is valid, and kept, with every reservation, once it has expired.
  const head = await storage.head(token.key);
  if (head.error) return fail(storageFailure(head.error, logger));
  if (head.data?.metadata["cloudrop-id"] === token.fileId) {
    if (nowSeconds() >= token.exp) return ok({ fileId: token.fileId });
    const removed = await storage.delete(token.key);
    if (removed.error) return fail(storageFailure(removed.error, logger));
  }
  await runOnAbort(config.plugins, [abortContext(token, "aborted")], logger);
  return ok({ fileId: token.fileId });
}
```

```ts
async function toRequest(request: NodeRequest): Promise<Request> {
  const headers = new Headers();
  for (const [name, value] of Object.entries(request.headers)) {
    // HTTP/2 pseudo-headers (":authority") are not header names a Request accepts.
    if (name.startsWith(":") || value === undefined) continue;
    for (const item of [value].flat()) headers.append(name, item);
  }
  const method = request.method ?? "GET";
  const body = method === "GET" || method === "HEAD" ? undefined : await readBody(request);
  return new Request(toUrl(request), { method, headers, body });
}

const UNREADABLE: ErrorResponse = {
  error: {
    code: "INVALID_INPUT",
    message: "The request could not be read. Check its method and URL, then send it again.",
    retryable: false,
  },
};

/**
 * Never rejects: Node ignores the listener's promise, so a rejection would be an unhandled rejection that stops the
 * process. Node accepts requests a fetch Request cannot hold (TRACE, an absolute URL with port 99999) and clients that
 * hang up mid-body; those get a 400, or nothing once the socket is gone.
 */
export function toNodeHandler(
  cloudrop: RequestHandler,
): (request: NodeRequest, response: NodeResponse) => Promise<void> {
  return async (request, response) => {
    const incoming = await toRequest(request).catch(() => null);
    const answer = incoming
      ? await cloudrop.handler(incoming)
      : new Response(JSON.stringify(UNREADABLE), {
          status: 400,
          headers: { "content-type": "application/json", "cache-control": "no-store" },
        });
    response.statusCode = answer.status;
    answer.headers.forEach((value, name) => {
      response.setHeader(name, value);
    });
    response.end(new Uint8Array(await answer.arrayBuffer()));
  };
}
```

## Owner decisions

1. **D20: may a live token delete a completed file?** After T10-1, `/abort` deletes this upload's own object only
   while the token is valid (24 hours), even after `/complete`. The alternative is to never delete a single-PUT object
   at `/abort`, which leaves orphans the lifecycle rule cannot clean. **Recommendation:** keep the 24-hour window (spec
   §5.5 requires the delete), document the token as a 24-hour delete capability in the `onComplete` TSDoc, and close it
   with the 1.1 database adapters, which know whether `/complete` ran. D4 is acceptable as it stands: `onComplete`
   receives `request`, so an app that must re-check a revoked session can do it there. Say so in the `onComplete`
   TSDoc.
2. **CI runs Node 22 while `engines` says `>=24`.** The owner changed `engines` on purpose. Today CI tests a runtime
   the package refuses, and never tests the one it requires. **Recommendation:** set `node-version: 24` in all four
   `setup-node` steps of `.github/workflows/ci.yml` in a separate `ci:` commit before M2 starts, and apply the spec §3
   edit 9 (T17-1).
3. **`biome.json` declares schema 2.6.7 while Biome 2.6.8 runs.** **Recommendation:** change `$schema` to
   `https://biomejs.dev/schemas/2.6.8/schema.json` in the same `chore:` or `ci:` commit. It removes the info line on
   every check and changes no rule.
4. **The server lane runs only on the fake and live R2.**
   - What the server does on a backend is the driver's behaviour, which the storage contract already runs on RustFS
     and Wrangler.
   - The server-specific paths (verification, `PARTS_MISSING`, idempotent `/complete`) are backend-independent and run
     on the fake.
   - Wrangler would need skips for its known gaps (`conditionalCompletion`, `responseOverrides`).

   **Recommendation:** do not add RustFS or Wrangler server lanes in M2. Record the decision in `test-backends.md` ("the
   upload-protocol lane runs on the fake and live R2; RustFS and Wrangler are covered through the storage contract"),
   and revisit in M3, whose chaos proxy and browser lane need a real backend server anyway.
5. **`route()` option order.** TypeScript infers `authorize`'s result only for callbacks written after it (T12-1).
   **Recommendation:** accept the constraint, document it in the TSDoc, and reorder spec §4. A builder API
   (`route(…).onComplete(…)`) would lift it at the cost of the one-object shape the spec's quickstart uses.
6. **Plain objects only from `authorize` (T7-1).** A class instance, such as a Mongoose document, now fails with a
   logged 500 instead of being signed into the token. **Recommendation:** accept it. It fails closed with a clear
   message, and `{ user: doc.toObject() }` is the fix.
