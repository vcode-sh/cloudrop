# cloudrop: design

Date: 2026-11-15. Status: approved design, updated with real-R2 spike results (§12).

cloudrop is an MIT TypeScript library for fast, resumable, direct-to-bucket file uploads to Cloudflare R2 and
S3-compatible storage. Background research: [`docs/research`](../../research).

## 1. Philosophy and success criteria

The reference points are Resend and better-auth: a developer gets everything they need, and using it takes a few
lines of code.

- **Five lines to a working upload.** One configuration call on the server, one handler to mount, one client whose
  types are inferred from the server.
- **Robust by default.** Retries, resume, verification and safe headers need no configuration. Options exist to
  tune, never to make it safe.
- **One instance, plugins extend everything.** A plugin adds server behaviour, client behaviour and types together.
- **Results, not exceptions.** Public calls return `{ data, error }`. `error` is a `CloudropError` with a stable
  `code`, a `message` that says what to do next, `retryable` and, where relevant, the `file`.
- **Secure without thinking.** Authorization is required by the types. Size, type and content are verified by the
  server. Keys are generated by the server.
- **Small and dependency-free.** Zero runtime dependencies. Client plus React under about 8 kB gzip.

The quickstart the docs open with:

```ts
// server: lib/cloudrop.ts
export const cloudrop = createCloudrop({
  storage: r2({ bucket: 'media' }),
  routes: {
    avatar: route({ accept: 'image/*', maxSize: '5MB', authorize: ({ request }) => requireUser(request) }),
  },
})

// app/api/cloudrop/[...all]/route.ts
export const { GET, POST } = toNextHandler(cloudrop)

// client
const { upload, files } = useUpload<typeof cloudrop>('avatar')
```

The client imports only the server's type (`import type`), never its code. `createCloudropClient` is needed only to
customize the client (base path, persistence, concurrency, plugins); hooks accept that client as an option.

## 2. Scope

**1.0:** headless client, React bindings, UI components through a shadcn registry, R2 plus generic S3-compatible
storage, stateless server with a `store` interface reserved for later adapters, four plugins (content checks,
checksums, limits, images), and an essential server file API.

**1.1:** database adapters, starting with Drizzle: a files table, exactly-once `onComplete`, cross-device resume,
orphan cleanup and built-in quota.

**Later, not designed here:** Vue and Svelte bindings, a Cloudflare Worker R2-binding driver, server-side streaming
multipart for large server uploads.

**Out of scope:** remote sources (cloud drives, URLs), image editing UI, a hosted service, webhooks as a requirement,
CommonJS builds, a tus server.

## 3. Package layout

One npm package, `cloudrop`, with subpath exports. One install and one version; no drift between server and client.

| Import | Contents | Runtime |
|---|---|---|
| `cloudrop` | `createCloudrop`, `route`, `r2`, `s3`, `allowAnyone`, types, `CloudropError` | Node 22+, Bun, Deno, Workers |
| `cloudrop/next`, `cloudrop/node` | `toNextHandler`, `toNodeHandler` | Server |
| `cloudrop/client` | `createCloudropClient`: store, queue, transports, persistence | Browser, React Native |
| `cloudrop/react` | `useUpload`, `useDropzone` | React 18 and 19 (optional peer) |
| `cloudrop/plugins` | `contentChecks`, `checksums`, `limits`, `images` (server halves) | Server |
| `cloudrop/client/plugins` | Client halves of the same plugins | Browser |
| `cloudrop/adapters/drizzle` | 1.1 | Server |

Internal modules, each testable on its own and reachable only through its interface:

1. **`protocol`**: request and response types for the four endpoints, error codes, token format. The only thing
   client and server share.
2. **`storage`**: the `StorageDriver` interface (`presignPut`, `createMultipart`, `presignPart`, `listParts`,
   `completeMultipart`, `abortMultipart`, `head`, `getRange`, `put`, `copy`, `delete`, `deleteMany`, `list`) and two
   implementations, `r2` and `s3`, built on our own SigV4 signer over WebCrypto. The `r2` preset encodes R2 rules:
   equal part sizes, no presigned POST, 7-day maximum presign expiry, S3 endpoint for presigned URLs.
3. **`server`**: the `Request → Response` router, HMAC tokens, policy, authorization, completion verification,
   plugin hooks, `api.*` and the `store` interface (stateless by default).
4. **`engine`**: a pure state machine, the part planner and the scheduler. No network, no DOM, deterministic under a
   fake clock.
5. **`client`**: transports (XHR for upload progress, fetch elsewhere), persistence (memory, IndexedDB, opt-in OPFS),
   optional Web Worker for hashing, sniffing and image work.
6. **`react`**: hooks over the client store via `useSyncExternalStore`.

Metadata schemas use Standard Schema, so users bring zod, valibot or arktype and cloudrop depends on none.

Repository: Bun workspaces with `packages/cloudrop`, `packages/registry` (shadcn components), `apps/docs`,
`examples/{next,hono,workers,vite-react}` and `test/contract`.

## 4. Server API

```ts
export const cloudrop = createCloudrop({
  storage: r2({ accountId, accessKeyId, secretAccessKey, bucket, publicUrl }), // env defaults: CLOUDROP_R2_*
  secret: [current, previous],          // HMAC secrets; an array allows rotation
  basePath: '/api/cloudrop',
  trustedOrigins: ['https://app.example.com'],
  routes: {
    avatar: route({
      accept: ['image/png', 'image/jpeg', 'image/webp'],
      maxSize: '5MB',
      maxFiles: 1,
      metadata: z.object({ albumId: z.string() }),       // any Standard Schema
      prefix: ({ user }) => `users/${user.id}/avatars`,
      visibility: 'public',                              // or 'private'
      authorize: async ({ request, metadata }) => {      // required; allowAnyone must be explicit
        const user = await getUser(request)
        if (!user) return unauthorized()
        return { user }
      },
      onComplete: async ({ file, user, metadata }) => ({ url: file.url }), // typed result returned to the client
    }),
  },
  plugins: [contentChecks(), limits({ ... }), images(), checksums()],
})
```

- `cloudrop.handler(request)` is the single adapter surface. Next.js, Hono, Workers, Bun, Elysia, SvelteKit, Remix
  and TanStack Start mount it in one line; `toNodeHandler` bridges Node `http`.
- `onComplete` runs inside the client's `/complete` request and its return value reaches the client, typed. Delivery
  is at-least-once with a stable `file.id`; the docs say so. The 1.1 adapters make it exactly-once.
- In development, startup warns about missing bucket CORS (`ExposeHeaders: ETag`), a missing abort-incomplete
  lifecycle rule, and private routes on a bucket with a public domain.

## 5. Upload protocol

Four JSON endpoints under `basePath`, each with a body cap. Bytes go from the browser straight to the bucket; the
server never handles them.

```
client                     server (cloudrop.handler)                  bucket
  │ POST /upload  {route, files[], metadata}                            │
  │──────────────▶ bounds → authorize → plugins.before → policy → plan ─▶ CreateMultipartUpload (multipart only)
  │◀────────────── per file: token, plan, first batch of signed URLs     │
  │ PUT bytes (parallel, retried) ──────────────────────────────────────▶│
  │ POST /sign    {token, parts[]}  → more or renewed URLs              │
  │ POST /complete {token}                                               │
  │──────────────▶ verify (ListParts | HEAD) → complete → plugins.after │
  │                → onComplete                                          │
  │◀────────────── { file, data }                                        │
  │ POST /abort   {token}  → AbortMultipartUpload or delete, release    │
```

### 5.1 Plan

The server decides; the client cannot.

- Files up to 64 MiB (configurable `multipartThreshold`) use one presigned PUT; larger files use multipart.
- Part size is the smallest of 8, 16, 32, 64… MiB that keeps the part count at or below 10,000. Every part except
  the last has exactly that size, so R2's equal-part rule holds by construction.
- The plan is stored in the token, so resume reproduces the exact part boundaries.

### 5.2 Upload token

- An HMAC-SHA256 signed, base64url token carrying
  `{ v, route, key, uploadId?, size, type, partSize, owner, metadataHash, fileId, exp }`.
- Every call after `/upload` must present it. The server ignores any key, size or upload ID that is not in the token,
  which rules out completion forgery and key rebinding without a database.
- Lifetime 24 hours by default; this is the resume window. Signed URLs live 15 minutes and are renewed through
  `/sign`, in batches (default 20 parts).
- Verification accepts any secret in the `secret` array, so secrets rotate without breaking live uploads.

### 5.3 Keys

- Generated by the server: `<prefix>/<ulid><ext>`. A route may supply `key: ({ file, user }) => string`; the result
  is still sanitized.
- Sanitizing rejects `.` and `..` segments, a leading `/`, control characters, and keys over 1024 bytes, and
  normalizes Unicode to NFC.
- The client's filename is used only in `Content-Disposition` (`filename*`, RFC 6266/5987), never in the key.

### 5.4 Idempotency

- Single PUTs carry a signed `If-None-Match: *`. A retried PUT that gets `412` means the first one landed; `/complete`
  confirms it.
- Every object carries `x-amz-meta-cloudrop-id` (the token's `fileId`). A retried `/complete` whose multipart upload
  no longer exists succeeds only after a `HEAD` shows the object with the matching ID and size.
- Multiple files in one `/upload` call share one round trip: a small file costs three requests (init, PUT, complete).

### 5.5 Abandoned uploads

The client calls `/abort` when a user cancels (abort is free on R2). Everything else is cleaned by the bucket's
abort-incomplete multipart lifecycle rule; `api.checkBucket()` verifies it exists.

## 6. Client resilience

### 6.1 Scheduler

- One pool shared by all files and parts. `concurrency: 'auto'` starts at 4, adds one connection while measured
  throughput rises, up to 8, and halves on `429`, stalls or network errors.
- At most 4 parts of one file in flight, so a small file never waits behind a large one. `order: 'smallest-first'`
  is available.
- Bytes are read with `Blob.slice`; the file is never loaded whole. Memory overhead is about part size times
  in-flight requests.

### 6.2 Failure classifier

| Condition | Response |
|---|---|
| Network error, 408, 429, 5xx, `SlowDown` | Retry with exponential backoff and full jitter (0.5 s to 20 s), up to 6 attempts, honouring `Retry-After` |
| Readable `403 ExpiredRequest`, or an unreadable CORS failure (an expired R2 URL may return no CORS headers) | Renew the signature once through `/sign`, then retry |
| Readable `403 SignatureDoesNotMatch` (bytes do not match the signed size, type or checksum) | Fail the file with `UPLOAD_REJECTED`; never retried |
| No progress for 30 s | Abort that request and retry the part |
| `offline` event | Pause; resume on `online` |
| Other 4xx, expired token | Fail the file with a code, for example `UPLOAD_EXPIRED` |

A failing part does not abort its siblings. A file fails only when a part exhausts its attempts; `retry()` then sends
only the missing parts.

### 6.3 Resume after reload

- Multipart uploads persist to IndexedDB by default:
  `{ fingerprint, token, plan, parts: [{ n, etag, checksum? }] }`. The fingerprint is name, size, `lastModified` and
  a hash of the first and last 64 KiB.
- `uploader.resumable()` lists unfinished uploads. When the user picks the same file again, only missing parts are
  sent.
- `persist: 'opfs'` copies the file into the origin-private file system so a reload resumes without re-selecting the
  file. It checks available quota first and deletes the copy when the upload finishes or expires.
- The client trusts its own record and does not call `ListParts` on resume (a paid Class A operation). `/complete`
  verifies everything and returns `PARTS_MISSING` with part numbers when something is absent; the client re-sends
  them.

### 6.4 Progress and control

- Bytes come from XHR `upload.onprogress`. Displayed progress never moves backwards: a re-sent part is not counted
  twice.
- Speed is an EWMA over about 3 seconds; ETA is remaining bytes over that speed.
- Snapshot: `{ files: [{ id, name, status, progress, bytes, size, speed, eta, error, result }], totals }`.
- `pause()`, `resume()`, `abort()` and `retry()` work per file and globally. Pausing aborts in-flight parts and loses
  at most one part of progress per connection.
- Optional `warnOnUnload`.
- `await upload(files)` resolves to `{ data, error }`; it never rejects for expected failures and never surfaces a raw
  storage error.

## 7. Security and verification

1. **Authorization.** `authorize` is required by the route type; public uploads need an explicit `allowAnyone`. Its
   result flows into the token and `onComplete`.
2. **Origin and CSRF.** The handler accepts same-origin requests and `trustedOrigins` only, requires
   `Content-Type: application/json` (cross-origin calls must preflight), and checks `Origin`.
3. **Input bounds.** Body at most 64 KiB; `maxFiles` (default 10); filenames at most 255 characters; metadata
   validated by its schema and size-capped.
4. **Policy before signing.** `maxSize`, `accept` (MIME and extension agree), file count, `prefix` per tenant.
5. **Signed headers.** Exact `content-length` and `content-type` on single PUTs, exact `content-length` per part,
   `If-None-Match: *` on single PUTs, `x-amz-meta-cloudrop-id`, and `content-disposition`: `inline` for raster images,
   video and audio, `attachment` for everything else including HTML, SVG and XML. That closes stored XSS through a
   public bucket domain by default.
6. **Verified completion, the real guarantee.**
   - Multipart: `ListParts`; part count, every part's size against the plan, and the total against the declared size
     must match. Completion uses the server's part list and ETags, never the client's.
   - Single PUT: `HEAD`; size, type and `cloudrop-id` must match.
   - On mismatch the object is deleted or the upload aborted, and the client gets `VERIFICATION_FAILED`.
   - On R2 a mismatched size or type is already rejected at upload time (§12). Completion verification stays for
     defence in depth, for S3-compatible backends that behave differently, and because R2 rejects bad part sizes only
     at completion.
7. **Secrets and errors.** Credentials stay on the server; tokens carry no secrets; presigned URLs cover one object,
   one method and 15 minutes; errors never include storage responses, other users' keys or stack traces.
8. **Private routes.** `visibility: 'private'` requires a bucket without a public domain; startup warns when the
   configuration contradicts it.

## 8. Plugins (1.0)

A plugin is `{ id, server?: hooks, client?: hooks, $Infer? }`. Hooks: `beforeUpload`, `afterVerify`, `onAbort`,
`extendRoute` (new route options with types), and client `prepareFile`, `beforePart`.

- **`contentChecks()`**: ranged GET of the first 4 KiB at completion, magic bytes checked against `accept`; rejects
  executables and HTML disguised as other types by default; optional quarantine (upload under `_pending/`, promote
  with a server-side copy after checks); `scan(file)` hook for a virus scanner.
- **`checksums()`**: CRC32C per part computed in a Web Worker and signed into the part URL as a header (R2 ignores it
  as a query parameter), so the bucket rejects corrupted bytes with `400 BadDigest`. End to end, the client compares
  its CRC64NVME of the whole file with the value R2 stores on every write (§12).
- **`limits()`**: `rateLimit` per owner; quota through `reserve` at `/upload`, `commit` at `/complete` and `release`
  at `/abort` or expiry, so quota cannot be overshot between signing and completion. A failing limiter rejects
  (fail-closed). In 1.0 the app supplies the callbacks; in 1.1 the database adapter does.
- **`images()`**: client-side resize and compression in a Worker (OffscreenCanvas); server-side dimension checks
  (`minWidth`, `maxWidth`, …) parsed from file headers (PNG, JPEG, WebP, AVIF, GIF), no native dependencies.

## 9. File API

`cloudrop.api.*` uses the same configuration and returns `{ data, error }`.

| Method | Behaviour |
|---|---|
| `getUrl(key, { expiresIn, download })` | Public domain: plain URL. Private: presigned GET whose expiry is rounded to a time window, so every viewer in that window gets an identical, cacheable URL. `download` sets the filename. |
| `head(key)` | `{ size, type, etag, uploadedAt, metadata }`; `null` only on 404. Network errors are errors, never "not found". |
| `put(key, body, { type })` | Small server-side upload (Blob, ArrayBuffer, string) up to the single-PUT limit. |
| `delete(key)`, `deleteMany(keys)` | Batches of 1,000 with per-key results `{ deleted, failed[] }`. |
| `copy(from, to)` | Server-side; `UploadPartCopy` above 5 GiB. |
| `deletePrefix(prefix)` | Deletes page by page, re-lists to prove nothing remains, returns the proof. For erasure requests. |
| `checkBucket()` | Report on CORS (`ETag` exposed), the abort-incomplete lifecycle rule and public-domain conflicts. |

## 10. Lessons carried over from earlier implementations

Audits of two private production codebases informed these rules (findings kept outside this repository):

- Never call storage inside a caller's database transaction; claim state first, then call the bucket.
- Sign `content-type`; an unsigned type lets a valid URL upload HTML to a public domain.
- Make single PUTs create-only (`If-None-Match: *`); otherwise a URL can overwrite the object until it expires.
- Reserve quota at signing time; checking it only at signing allows overshoot until completion.
- `exists`/`head` must not map network errors to "not found"; `deleteMany` must report per-key errors and batch over
  1,000.
- Do not sign every part URL up front; sign lazily in batches with short expiry.
- Parallelize parts within a file; one-at-a-time parts leave most of the bandwidth unused.
- Retries need jitter and `Retry-After`; an expired R2 URL surfaces as a CORS error, not a readable 403.
- A declared checksum must never trigger a full-object re-hash on the server under a short timeout.
- Bucket CORS and lifecycle rules must be verified by code, not assumed from docs.

## 11. Testing

1. **Unit (Vitest):** state machine and scheduler under a fake clock; part planner with property tests; SigV4 signer
   against AWS's published test vectors; token encode, verify and rotation.
2. **Contract:** one suite in `test/contract` run against an in-process fake encoding R2's rules (every commit), the
   Wrangler local S3 endpoint and RustFS (every pull request), and a real R2 bucket (nightly and before every release,
   with a dedicated bucket and CI-only credentials).
3. **Chaos:** a fault-injecting proxy (dropped connections, 429, 503, latency, truncated responses, expired URLs). A
   run passes when every upload ends correct or with a clear error code.
4. **Browser (Playwright):** progress, pause, reload-resume with IndexedDB and OPFS, offline and online, CORS.
5. **Types:** inference tests (`expect-type`) for route names, metadata and the `onComplete` result.
6. **Package:** size-limit, publint and attw on the packed tarball.

CI runs on GitHub-hosted runners: npm trusted publishing requires them.

## 12. Real-R2 spike results (2026-11-15)

Evidence: [`docs/research/r2-spike-findings.md`](../../research/r2-spike-findings.md). Decisions they settle:

| Finding on real R2 | Decision |
|---|---|
| A signed `content-length` or `content-type` mismatch on presigned PUT and presigned `UploadPart` gets `403 SignatureDoesNotMatch` and stores nothing. Unsigned length is not enforced. | Size and type are rejected at upload time. §7.6 verification stays as defence in depth and for non-R2 backends. |
| Signed `If-None-Match: *` gives `412` on an existing key; omitting a signed one gives `403`. On `CompleteMultipartUpload` an existing key gives `412` and discards the upload. | Create-only single PUTs as designed. Multipart completion also sends `If-None-Match: *`; keys are unique, so a `412` there means a key collision and fails the file. |
| Larger last part, unequal middle part and a non-last part under 5 MiB are accepted by `UploadPart` and rejected only at completion (`InvalidPart`, `EntityTooSmall`); the upload survives and can be repaired. | The server's pre-completion `ListParts` check is required, not optional. It returns `PARTS_MISSING` (with part numbers) for absent or wrong-sized parts and the client re-sends them. |
| A signed `x-amz-checksum-crc32c` or `-crc64nvme` header is validated (`400 BadDigest`); the same value as a query parameter is silently ignored. Completion does not validate composite checksums. R2 stores a full-object CRC64NVME on every write. `GetObjectAttributes` returns 501. | `checksums()` ships: per-part CRC32C signed as a header, never as a query parameter. The server compares `ListParts` CRC32C values with the client's, and the client compares its own CRC64NVME of the whole file with the one R2 reports, for end-to-end integrity. |
| The AWS SDK presigner adds an empty-body checksum to URLs by default and does not sign `content-type`. | Confirms our own signer, which signs exactly the headers the client sends. |
| Expired URL: `403 ExpiredRequest`. Maximum expiry 604800 s; 604801 gives `400`. | `r2` preset caps expiry at 7 days. A readable `ExpiredRequest` re-signs; a readable `SignatureDoesNotMatch` fails the file with `UPLOAD_REJECTED` (never retried). |
| 8 parallel parts on one key: no throttling. 5 concurrent PUTs to one key: one `429` with S3 code `ServiceUnavailable`, not `TooManyRequests`. | The retry classifier keys on HTTP status (429, 503), never on the S3 code. Part concurrency per file stays at 4. |
| `ListParts` returns ETag, Size, LastModified and CRC32C when sent; `max-parts` pagination works; after completion it returns `NoSuchUpload`. A retried completion returns `404 NoSuchUpload`. HEAD shows custom metadata, type, part count and a `-N` ETag. | Confirms the idempotent `/complete` design in §5.4. |
| Signed `content-disposition` is stored and served by both the S3 endpoint and the public domain. Ranged GET returns 206 with a correct `Content-Range`. | Confirms the XSS defence in §7.5 and the 4 KiB sniff in `contentChecks()`. |
| `CopyObject` keeps type, disposition and metadata; copying a multipart object replaces its ETag with a plain MD5; a copy is one Class A operation. | Quarantine promotion works. Nothing may treat an ETag as stable across promotion; `cloudrop-id` is the stable identity. |

Still unverified, and required before 1.0 in the browser lane:

1. Browser uploads end to end (presigned PUT and parts, reading `ETag`), and whether an expired URL's `403` carries CORS
   headers. Blocked until the test bucket has an upload CORS rule.
2. More than 8 parallel parts on one key.
3. AWS chunked uploads with trailing checksums (not used by cloudrop's browser path).
4. The bucket's lifecycle rules (the test token cannot read them); `checkBucket()` must use an account-level token.

## 13. Release

- ESM-only; explicit `exports` with `browser`, `workerd` and `default` conditions; `sideEffects: false`;
  `isolatedDeclarations`; tsdown builds.
- Changesets; npm trusted publishing (OIDC, provenance) from GitHub-hosted runners.
- 0.x releases under the `next` tag until the API freezes. 1.0 ships when the contract suite passes on real R2 and
  chaos tests pass.
- `SECURITY.md` with private vulnerability reporting, a threat-model page, `llms.txt`, docs opening with the
  five-line quickstart.
