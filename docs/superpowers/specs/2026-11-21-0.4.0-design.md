# 0.4.0: content checks, delete hooks, file filters and the account guard

Status: approved for implementation, 2026-11-21 (the owner chose this scope after 0.3.0). Rulings are recorded as
`M10-<letter><n>` in the files named per part. Source: the API review after 0.3.0 and the pilot's own code.

## 1. `cloudrop/plugins` and `contentChecks()` (`M10-K`, `docs/decisions/m10-content.md`)

**Problem.** The server trusts the type the browser declares. A page can upload HTML or an executable as `image/png`,
the route's `accept` lets it through, and the bucket stores it with that type.

**Build.** A new entry `cloudrop/plugins` (server halves; zero dependencies, its own size budget, imported by no other
entry) exporting `contentChecks(options?)`, a plugin on the existing `afterVerify` hook (design spec §8):

- At `/complete`, after the server verified size and parts, read the first 4 KiB with `storage.getRange` and detect the
  type from its magic bytes: at least PNG, JPEG, GIF, WebP, AVIF/HEIC (ISO BMFF brands), PDF, ZIP and its office
  formats, MP4/MOV, WebM/Matroska, MP3, WAV, OGG, FLAC, and a text sniff for HTML, SVG and XML. Primary sources for
  every signature (the format's spec or the WHATWG MIME Sniffing standard), cited in the code.
- Refuse a file whose detected type is not allowed by the route's `accept`, a declared type the content contradicts,
  and by default anything that sniffs as HTML, an executable (PE, ELF, Mach-O) or a script, whatever its declared type.
  SVG is refused unless the route accepts `image/svg+xml` explicitly. A type the sniffer cannot recognise passes only
  when the route accepts it by its declared type and it is not refused above; say so in the guide.
- A refused file ends `rejected`: its object is deleted (only when it is this upload's, as everywhere), `onAbort` runs
  for the plugins, the store releases its quota, and the client gets a clear, non-retryable error (an existing code if
  one fits, else a new one added to the code union and `errors.md`).
- Options kept small: `allow` / `deny` overrides by type, and nothing for quarantine or virus scanning yet (later).
- Measured on R2 that a ranged GET of an object of fewer than 4 KiB, and of 0 bytes, behaves as the code expects.

## 2. `onDelete` route hook (`M10-D`, `docs/decisions/m10-delete.md`)

**Problem.** `deleteFile`, `replace`, `eraseOwner` and the sweep delete completed files without telling the app; the
pilot had to write its own deletion path to keep an audit trail and its pointers right.

**Build.** A route hook `onDelete({ file, owner, reason, tx? })`, `reason` one of `"deleted"` (`api.deleteFile`),
`"replaced"` (`replace: true`), `"erased"` (`api.eraseOwner`). It runs when a completed file's row becomes `deleted`,
in the same transaction as that change when the store has `transaction: true` (so a pointer or an audit row commits
with it, exactly once), and under the same rules as `onComplete` otherwise (state the guarantee per mode). A throw in
transaction mode rolls the deletion back and the call answers an error; say what each caller then does. Only with a
store. Document it in the store guide beside `onComplete`, with the pilot's audit-trail case as the example.

## 3. `api.files` filters (`M10-D`, same file)

`api.files({ owner, route?, name?, type?, order?, limit?, cursor? })`: `name` matches a case-insensitive substring of
the file name (ASCII case folding is enough; escape `%` and `_`; identical results on Postgres, SQLite and D1, and in
the memory store), `type` is an exact type or a top-level prefix such as `"image/"`, and `order` is `"newest"` (the
default) or `"oldest"`. The cursor stays opaque and is refused when it belongs to other filters or another order. No
listing across owners in this release (it needs another index).

## 4. The account guard (`M10-A`, `docs/decisions/m10-account.md`)

**Problem.** When another tab signs in as someone else, a file still queued in this tab can start `/upload` with the
new session's cookie and become the other account's file. The pilot closed this by hand with a header.

**Build.** A client option `account` (a string, or a function returning one) sent with `/upload` only, as a header
such as `x-cloudrop-account`. On a route with a store and `owner`, the server compares it with `owner()`'s answer and,
when both are present and differ, refuses the whole request with a new non-retryable code (for example
`ACCOUNT_CHANGED`) whose message tells the person to reload the page. A request without the header is checked as
before (older pages keep working during a deploy). The handler's own CORS preflight must allow the header; prove it
with a preflight test. The React factory passes it through. Document it in the React "Signed-in users" recipe, which
then needs no hand-written header.

## 5. Error copy in the React guide (`M10-A`, same file)

The React guide's error section says what to show for `CLIENT_CLOSED` (an upload picked while signing out) and for
`ABORTED` (nothing: the row already says it was cancelled), and for `ACCOUNT_CHANGED`, as the pilot found.

## Out of scope

Quarantine and virus scanning, `limits()`, `images()`, `checksums()`, listing across owners, "attach on submit",
server-side uploads with a row.
