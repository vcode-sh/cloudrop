# 0.6.0: what the pilot's move to 0.5.0 could not do, and a review of every area

Status: approved for implementation, 2026-11-21. The owner's terms: fix every gap the pilot reported, review every file
and flow, and release nothing until the pilot passes on the unpublished candidate and the owner has read the summary.
Source: the pilot's migration report (vstack branch `cloudrop-050`). Rulings are recorded as `M11-<letter><n>` in the
files named per part.

## 1. `api.deleteFile` says what it did (`M11-D`, `docs/decisions/m11-delete.md`)

**Problem.** `deleteFile` answers `{ id }` for a file it deleted and for one already deleted, so a caller cannot tell
whether its own call deleted the file; and when the row was deleted but the object's removal failed it answers an
error, although the file is gone for the owner. The pilot passes a mutable slot through `context` and re-reads the row.

**Build.** `deleteFile` answers `{ id, deleted, cleaned }`:

- `deleted`: true when this call moved the row from `completed` to `deleted`; false when it already was.
- `cleaned`: true when the row is marked cleaned (the bucket was checked after the file's URLs and grace ran out and
  holds nothing of it); false while the sweep still has to check it again.
- A storage failure while removing the object of a row that is already `deleted` (by this call or an earlier one) is
  logged and answers success with `cleaned: false`: the sweep removes the object. A store failure still answers the
  retryable `SERVER_ERROR`. `NOT_FOUND` as before.

## 2. `onDelete` can refuse (`M11-D`, same file)

**Problem.** A throw is the hook's only way to keep a file: it is logged as an error and answers a retryable
`SERVER_ERROR`, so an app rule such as "an administrator's file may not be deleted" needs a second, unlocked check
before the call, and a refusal found under the hook's own locks reads as an outage.

**Build.** A route's `onDelete` may **return** a `CloudropError`: a refusal.

- The file is kept. With a transaction, the transaction rolls back, so the hook's writes are undone.
- Nothing is logged as an error.
- `api.deleteFile` answers that error as it is (its code, message and `retryable`).
- `api.eraseOwner` counts the file in a new `refused` counter of its report and in `waiting` (it is still completed),
  goes on with the next file and reports `done: false`.
- A replacing `/complete` answers the refusal to the client in place of the generic `SERVER_ERROR`: the completion is
  not recorded and the previous file stays, as with a throw. Under a lease `onComplete` has already run, as with a
  throw; the guide says so.
- A **thrown** error, a `CloudropError` included, stays a failure (logged, retryable `SERVER_ERROR`): an error rethrown
  from a cloudrop call inside the hook must never pass for the app's refusal.
- Any other returned value than `undefined` or a `CloudropError` is the hook's bug: treated as a throw, with a log line
  that says what it returned.
- A lease-mode late replacement's hook (run after the record) cannot refuse: a returned error is logged, as a throw is.

## 3. A content refusal says what the file is (`M11-K`, `docs/decisions/m11-content.md`)

**Problem.** `contentChecks()` refuses with an English sentence only. An app that translates its errors cannot say
"this is a JPEG" in its own words.

**Build.** A `FILE_TYPE_NOT_ALLOWED` error from `contentChecks()` carries `content`, which reaches the client beside
`code`, `message` and `retryable` (as `parts` does for `PARTS_MISSING`):

```ts
content?: {
  /** The type the file was sent as. */
  declared: string;
  /** The type its first bytes show; absent at `/upload`, where no bytes exist yet, and when they show none. */
  detected?: string;
  /** "mismatch": the content is another type than declared. "refused": a kind refused on this server (a web page,
   *  a program, a script, an XML type the route does not name, a `deny` entry). "not-accepted": the content's own type
   *  is not in the route's `accept`. */
  reason: "mismatch" | "refused" | "not-accepted";
}
```

Both hooks set it: `/upload` (by declared type, `reason: "refused"`, on the request-level error) and `/complete`. The
wire body gains `content`; the client and `cloudrop/react` expose it on `CloudropError.content`; an older client
ignores it and an older server sends none. The route's own `accept` refusal (no plugin) stays as it is. Only these
three strings and two MIME types: never bytes, keys or names.

## 4. The command reads an app's own variable names (`M11-C`, `docs/decisions/m11-command.md`)

**Problem.** `cloudrop doctor` and `setup` read only `CLOUDROP_*`. An app that names its settings otherwise wraps the
command in a script that renames them.

**Build.** `--var <SETTING>=<NAME>`, repeatable, for both commands: read the setting `CLOUDROP_R2_BUCKET` from the
variable `R2_BUCKET`. `SETTING` must be one of the settings the command reads; `NAME` a valid variable name.

- Every message, note and printed command then names the app's variable (`R2_BUCKET`), never the cloudrop name it
  stands for, and still never a value.
- Service detection, the env file, the misspelling notes and "set in both" notes work on the mapped names. A mapped
  setting does not also read its `CLOUDROP_*` name.
- A usage error (exit 2) for an unknown setting, a malformed pair, a setting mapped twice or two settings mapped to one
  variable.
- The library itself is unchanged: `createCloudrop`, `r2()` and `s3()` take options for other names.

## 5. Review of every area (`M11-R`, `docs/decisions/m11-review.md`)

Each area is read file by file and flow by flow by a reviewer who did not write it, against the design, the decisions
and the measured R2 behaviour: storage, the server protocol, the store and its adapters, the client engine, React, the
command, the plugins, `cloudrop/testing`, the examples and the guides. A finding counts only with a failing input, a
probe or a test that shows it. Every confirmed finding is fixed with a test in this release or, when it is a design
choice, recorded with its reason. Then every gate, then the pilot on the packed candidate.

## Out of scope

Listing across owners (needs a new index and a migration of every store; the pilot's admin inventory also joins its
own user table, so it would keep its query), a comma-separated list in `CLOUDROP_SECRET`, `limits()`, `images()`,
`checksums()`, quarantine.
