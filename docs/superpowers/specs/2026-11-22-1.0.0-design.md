# 1.0.0: a complete package, simple to use, frozen under semver

Status: approved by the owner, 2026-11-22, with four changes recorded in "The owner's rulings on the draft" below. Rulings are recorded as `M12-<letter><n>` in the files named per part
(a new milestone series, with rows in `docs/decisions/README.md` and the series list in `AGENTS.md`).

## The owner's rulings on the draft (2026-11-22)

- **Node 26 is the minimum**, everywhere: `engines`, CI, the release workflow, examples, scripts, docs. Not Node 24
  and 26 as part 8 first said.
- **TypeScript 7 is the minimum** for the shipped types. A CI job type-checks the packed `.d.ts` with TypeScript
  7.0.0, not 5.7. The reference and the freeze guard (part 8) read the `.d.ts` through TypeDoc and api-extractor, which
  bundle the JavaScript TypeScript 6 compiler; that is a dev tool only and is not the floor.
- **Size ceilings are raised** so they guard against accidents and never block work. The new ceilings are in the plan;
  the release summary reports the measured sizes.
- **Everything else is modular.** Optional parts stay behind their own entries, so an app pays only for what it
  imports: `cloudrop/store` (part 5), `cloudrop/plugins`, the adapters, `cloudrop/testing`, `cloudrop/react`.

## Why this release, and what it is not

The owner's terms (2026-11-22):
- the next release is 1.0.0, with no intermediate 0.7 or 0.8;
- every feature must earn its place by what applications actually write around cloudrop;
- the developer experience must be very simple;
- cloudrop ships no UI: users build their own.

Three sources shaped the scope:
1. **The pilot's integration** (about 2,300 lines of production code in the vstack app). About two thirds of it is the
   app's own business rules. About 260 lines are glue every app would write again, and about 250 lines work around
   things cloudrop lacks. Parts 1 to 6 replace those two groups.
2. **The landscape** (UploadThing, better-upload, pushduck, Uppy, tus, Vercel Blob, Supabase Storage, Cloudflare's R2
   guidance, small S3 helpers, surveyed 2026-11-22). Table stakes are:
   - per-route limits checked on the server;
   - an auth hook that can refuse;
   - a completion hook;
   - client success and error callbacks;
   - multipart;
   - a React hook;
   - delete and list helpers.

   The good libraries deliberately leave admin dashboards, cross-owner search, UI and media processing to the app.
3. **An audit of the public surface** against the base spec. It found:
   - names that must change before they are frozen;
   - a quickstart of about 45 lines;
   - store code that stateless apps pay for;
   - no stability policy, threat model, `llms.txt` or API reference.

**Cut from 1.0 by the owner (2026-11-22):** the `limits()`, `checksums()` and `images()` plugins. The virus-scan and
quarantine plugin the base spec gave `contentChecks()` goes too: a ten-line recipe covers it (part 8).

**Withdrawn because the evidence does not support them:**
- the `api.allFiles` filters and an `owners` hook. The pilot's admin inventory searches with one `OR` across cloudrop's
  rows and its own user table, joins its avatar table, reads roles, and must work while storage is not configured. Its
  own SQL over a documented table (part 7) is the right tool. No surveyed library offers this.
- a value handed back from `onDelete`. It would save the pilot 4 lines at the cost of a union type over every route.
- a `close()` timeout. The pilot never wraps `close()`. The full wait happens only when the API is down, and then the
  sign-out request fails anyway. What it lacked was a documented promise (part 3c).

Base spec §2, §3 and §8 are amended in the same change: the three plugins and `cloudrop/client/plugins` leave the 1.0
scope.

## 1. React: start errors and completion callbacks (`M12-H`, `docs/decisions/m12-hooks.md`)

**Problem.**
- A start the client refuses before it has a file row (`CLIENT_CLOSED`, `INVALID_INPUT` for its arguments,
  `INVALID_CONFIG`) never reaches the hook: the pick or drop handler drops the promise (`react/use-upload.ts:68-74`).
  The pilot wraps `start`/`resume` in 68 lines for this.
- There is no callback when a file ends. The pilot compares `totals.done` with a ref to refresh its queries.

**Build.**

```ts
interface UseUploadOptions<TMetadata, R = unknown> {
  metadata?: TMetadata;
  multiple?: boolean;
  accept?: string;
  /** A file of this route ended done, on its first try or after retry(). Called while the component is mounted. */
  onUploaded?: (file: Extract<FileOutcome<R>, { status: "done" }>) => void;
  /** A file of this route ended failed (error.file is set), or a start was refused without a file row (error.file
   *  is undefined). Never called for a cancel. */
  onError?: (error: CloudropError) => void;
}
interface UseUploadResult<R, TName, TMetadata> {
  // ...existing fields
  /** The route's last start refused without a file row; cleared by the route's next start and by clear(). */
  startError: CloudropError | null;
}
```

- **Route-wide, like `files`.**
  - Two mounted components on one route each get the callbacks.
  - `startError` is per route, guarded by a per-route sequence number, so only the latest start sets it.
- **Detected in the route's store, not in the hook.**
  - A status change from not-`done` to `done`, or from not-`failed` to `failed`, is an event once per store.
  - The baseline taken on `subscribe` reports nothing. A file that ended while nothing was mounted is never reported late;
    its row still shows the outcome.
- **Delivery.**
  - Callbacks are read from the latest committed render, as options already are.
  - Each hook registers in an effect, so StrictMode's double effect still gives one call per mounted hook.
  - The events of one publish go out in one microtask after the view listeners ran, so a callback may call `upload()`
    or `retry()`.
  - A callback that throws is rethrown in a task and does not stop the others.
- **The non-React client is unchanged:** `job.done`, `job.subscribe` and `retry()`'s promise already cover it.

**Size.** About +0.4 kB on `cloudrop/react` (2.26 → about 2.65 of 3 kB).

**Tests.** A new `react/use-upload-callbacks.test.ts` (unit lane, happy-dom). Each row:
- `CLIENT_CLOSED` after `close()` sets `startError`, sends no `/upload` and calls `onError` once; the next good start
  clears it;
- a failed PUT, then `retry()`, calls `onError` once, then `onUploaded` once;
- under StrictMode each event fires once;
- nothing is reported on a remount;
- a callback that calls `upload()` works;
- two components on one route are each called once;
- the latest render's callback is the one called.

## 2. Server refusals (`M12-E`, `docs/decisions/m12-errors.md`)

### 2a. `authorize` may return a `CloudropError`, and `rateLimited(seconds)`

**Problem.**
- `authorize` may return only a plain object, `unauthorized()` or `forbidden()`. Any other object is a `TypeError` and a
  500 (`server/upload.ts:89-96`).
- The pilot therefore smuggles `retryInSeconds` and `startUnavailable` through the signed auth object and turns them
  into errors in a plugin.
- A plugin's `RATE_LIMITED` answers 503 with no `Retry-After` (`server/http.ts:17,111`).

**Build.**
- `authorize` returns `TAuth | Refusal | CloudropError`.
- New export `rateLimited(seconds, message?)`:
  - It answers `RATE_LIMITED`, retryable, with `Retry-After = max(1, ceil(seconds))`.
  - A non-finite or negative `seconds` throws a `TypeError`, an app bug logged as a 500.
  - The default message is `Too many upload requests. Try again in N seconds.`
- `authorize` and `beforeUpload` may answer only these codes:

  | Code | Status |
  |---|---|
  | `UNAUTHORIZED` | 401 |
  | `FORBIDDEN` | 403 |
  | `QUOTA_EXCEEDED` | 403 |
  | `RATE_LIMITED` | 429, with `Retry-After` |
  | `FILE_TOO_LARGE`, `FILE_TYPE_NOT_ALLOWED`, `TOO_MANY_FILES`, `INVALID_METADATA`, `INVALID_INPUT` | 400 |
  | `SERVER_ERROR` (the app's own `retryable` kept) | 500 |

  - Any other code is answered as the generic non-retryable `SERVER_ERROR`, and the log names the code and the allowed
    list.
  - An allowed error is rebuilt from its code, message, `retryable`, `content` and wait, so `parts`, `file` and `cause`
    never leave the server.
  - A returned refusal is not a failure and logs nothing.
  - A `CloudropError` from another installed copy of cloudrop gets the "install cloudrop once" `TypeError`, as plugins
    already do.
- **`RATE_LIMITED` is 429 from every source**, storage throttling included:
  - one status per code;
  - a 503 can make a load balancer eject a healthy app server;
  - the chaos expectation `POST /complete 503` changes.
- **The wait travels on the error.**
  - A module shared by server and client (`src/retry-after.ts`) holds `waitAtLeast`, `retryAfterOf` and
    `parseRetryAfter`.
  - It replaces the `BUSY` set in `http.ts`.
  - `errorResponse` sets `Retry-After` from it and exposes the header cross-origin.
- **The client stops on a long wait.** When the recorded wait exceeds its 20-second backoff cap (`client/retry.ts:15`),
  `withRetry` and the per-file re-ask stop retrying. The error comes back as a retryable `RATE_LIMITED`, which the app's
  `retry()` honours later. Today `rateLimited(600)` would be retried five times, 20 s apart.

### 2b. `Retry-After` on the 200 that refuses a file storage could not start

This closes the debt in the plans README ("Chaos plan follow-ups"), still open: nothing in `storage/` reads the header.
1. The S3 transport passes the response's `retry-after` to `storageError`, which records the wait on a retryable error.
2. `storageFailure` keeps the wait.
3. Each rejected ticket keeps its wait.
4. `handleUpload` answers the 200 with the largest wait among the retryable rejected tickets.

The client already applies it per ticket (`client/endpoints.ts:213-215`). There is no wire change and no server cap; the
client's rule from 2a decides.

### 2c. `kind` on a content refusal

**Problem.** The pilot re-derives "program", "script" and "web page" from MIME types, copying `contentChecks()`'s
private lists, and its copy has already drifted.

**Build.** `content.kind?: "web-page" | "program" | "installer" | "script" | "svg" | "xml" | "denied"`.
- Set only with `reason: "refused"`, at the three refusal sites in `plugins/content-checks.ts`, and derived from the
  lists that file already holds.
- A category wins over `denied`: `deny: ["text/html"]` still says `web-page`.
- **Compatibility.** The server's `errorBody` and the client's `readContent` copy `kind` only when it is in the closed
  set and the reason is `refused`; otherwise `kind` alone is dropped and `content` kept. An older client drops it; an
  older server sends none. This amends `M11-K3` and `M11-K4`.

### 2d. A clear error for a bucket the browser cannot reach (`BUCKET_BLOCKED`)

**Problem.** The most common newcomer mistake is a missing or wrong CORS rule. It shows as a retryable `NETWORK_ERROR`
after about 15 seconds of retries. A rule that misses the origin or a signed header fails the preflight, so no byte of
the body leaves the page (`docs/research/r2-spike-findings.md`).

**Build.** A part, or a single PUT, fails at once with the new code `BUCKET_BLOCKED` (not retryable) when all of these
hold:
1. Two consecutive attempts on it ended in XHR `onerror`, which excludes cloudrop's own stall abort and `ontimeout`.
2. Neither attempt reported any upload progress (`loaded > 0`).
3. A `/sign` renewal of that part answered 2xx between them, so the upload server answers and the second URL was fresh.
4. `navigator.onLine !== false`.
5. Only on the XHR path. With a `fetch` option or outside a browser, the behaviour is unchanged.

The rule covers these cases:

| Case | Outcome |
|---|---|
| Really offline | Caught by 3 and 4 |
| Captive portal | Caught by 3: no readable cloudrop JSON |
| Firewall or extension that blocks only the storage host | Fires, correctly: retrying cannot help, and the message names the cause |
| Bad signature or expired URL | Sends the body, so 2 fails and the behaviour is unchanged |

The message names the CORS rule and `npx cloudrop doctor --origin <origin>`. `BUCKET_BLOCKED` keeps the ticket (it goes
in `KEEPS_TICKET`), so `retry()` after the rule is fixed reuses the parts already stored. Detection takes about two
round trips, against about 15 seconds today. This closes the open decision "Unreadable R2 refusals" in the plans README
for the case that matters. A bad-signature 403 stays a `NETWORK_ERROR`.

**Tests.**
- **Unit lane:** `client/bucket-blocked.test.ts` on the fake XHR. Each row:
  - the rule fires with exactly one `/sign` and no `/complete`;
  - progress before the failure gives the old `NETWORK_ERROR`;
  - a stall, offline or a failed `/sign` gives no `BUCKET_BLOCKED`;
  - a `fetch` option changes nothing;
  - `retry()` reuses the ticket.
- **Browser chaos lane:** the proxy answers the preflight 403 without CORS headers. The oracle is that no PUT reaches
  RustFS, the request log shows PUT, `/sign`, PUT, and the status shows `BUCKET_BLOCKED` within 5 s. The existing opaque
  403 row must stay green.
- **Live R2, once:** a page on an origin the test rule does not list, with the findings recorded. The owner's CORS rule
  is not changed.
- **Not measured yet:** Firefox and Safari, and whether R2's bad-signature answer shows upload progress for a tiny body.
  Both are measured in the browser lane before release.

## 3. Types that need no guards (`M12-T`, `docs/decisions/m12-types.md`)

### 3a. Typed `auth` in plugins, typed `context` for deletions

**Problem.**
- `auth` in plugin hooks is `unknown`, which forces the pilot's `isUploadActor` guard.
- The deletion `context` is `unknown`, which forces its `deleterOf` guard (14 lines).

**Build.**
- **Plugins.** `CloudropPlugin<TAuth = unknown>` carries a contravariant type-only member.
  - `createCloudrop` checks each plugin against the union of every route's `authorize` result. A plugin typed for
    `{ userId: string }` does not compile beside a route that can authorize without one.
  - `contentChecks()` stays `CloudropPlugin<unknown>`.
- **Every plugin hook receives the signed JSON snapshot** (`Jsonified<TAuth>`), never the live object. Today
  `beforeUpload`, `afterVerify` and `onAbort` differ, so one type is true everywhere only after this change.
- **Delete context** is declared per route and inferred from `onDelete`'s parameter annotation.
  - `DeleteContext<TDeleted, TErased>` is a union by `reason`.
  - `api.deleteFile` and `api.eraseOwner` take the intersection over the routes.
  - Their `context` becomes required when the declared type does not admit `undefined`.
  - Without annotations everything stays `unknown` and optional, as today.
  - Declaring it once on `createCloudrop` was rejected: a type argument there turns off inference of the routes.
- **Before building:** a type test prototypes the inference through `TExtra`. If it fails, the fallback is exported
  generics without the cross-check.

### 3b. `FileRecord` as a union by status

Each status gets its exact shape, derived from the store's writes:

| status | claimedAt | completedAt | endedAt | cleanedAt | result |
|---|---|---|---|---|---|
| pending | null | null | null | null | null |
| completing | Date | null | null | null | null |
| completed | Date | Date | null | null | string \| null |
| deleted | Date | Date | Date | Date \| null | string \| null |
| aborted, expired | null | null | Date | Date \| null | null |
| rejected | Date | null | Date | Date \| null | null |
| failed (never started) | null | null | Date | Date \| null | null |
| failed (stuck completion) | Date | null | Date | Date | null |

- `RecordOf<S>` extracts one status.
- `api.files` answers `CompletedRecord[]`, and `allFiles({ status: S })` answers `RecordOf<S>[]`.
- The store contract gains an `expectWellFormed(record)` oracle on every record it reads, on every backend.
- There are no database CHECK constraints for these invariants in 1.0, because of the migration cost.

### 3c. Route names and store methods in the types

- **Route names.** `route` on records and in the `api` filters is the server's route names (`keyof TRoutes & string`),
  not `string`. The guide says to keep a retired route declared, with an `authorize` that refuses, until its rows are
  erased.
- **Store methods.** `api` has the store methods only when a store is configured. Leaving out `store` infers a type
  without them. At runtime a store-less server keeps one shared stub that answers `INVALID_CONFIG`, for JavaScript
  callers.
- **`close()`, documented and not changed.** The client guide and the React guide's "Signed-in users" gain this
  paragraph, confirmed against `client/close.ts`, `launch.ts` and `server/abort.ts`:

  > An app need not wait for `close()` to move on. What it started runs to its end whether or not anything awaits it:
  > a ticket that an `/upload` in flight brings back later still gets its `/abort`, sent with that upload's own token,
  > so the server accepts it whoever is signed in by then; a `/complete` in flight still finishes for the user who
  > started it. An app can drop the promise, call `forget()` and create the next client at once: a late ticket saves no
  > record. The cost: if the app's `headers` function fails once the user signed out, a late `/abort` is not sent and
  > that upload waits for the lifecycle rule or the sweep.

## 4. Erasing an owner in one call (`M12-O`, `docs/decisions/m12-erasure.md`)

**Problem.** Erasing an owner today needs about 130 lines in the pilot:
- a scan for owners without a user row;
- two `eraseOwner` passes around a usage watermark, which covers the race `M8-A5` leaves open: an `/upload` that passed
  `authorize` before the account was deleted reserves a file after the last read;
- `deletePrefix` per folder;
- its own marker table.

The watermark compares timestamps from different clocks. `deletePrefix` cannot remove a multipart upload; only the
bucket's lifecycle rule does.

**Build: a durable erase mark on the owner's usage row.**

```ts
interface CloudropOptions { erase?: { prefixes?: (owner: string) => readonly string[] } }
api.eraseOwner(owner, { graceMs?, signal?, context? })   // EraseReport gains requestedAt and prefixed
api.reopenOwner(owner)                                    // → { reopened: boolean }
// SweepReport gains erasing and erased; api.usage gains erasure: { requestedAt, erasedAt | null } | null
```

1. **Mark.** The call upserts the usage row (zeros if there is none) and sets `erase_requested_at` once. An owner
   already erased answers `done` at once, which replaces the pilot's marker.
2. **Refuse new uploads.**
   - Once the mark is committed, `reserve` answers a new outcome, `"erased"`, for every file of that owner. The client
     receives `FORBIDDEN`.
   - The check runs under the same usage-row lock as the quota check, so a reserve either commits before the mark,
     and the row passes see its rows, or it is refused.
   - This closes `M8-A5`'s race and makes `done` durable.
3. **Row passes.** As today (`erase.ts`), with `lastReads` kept.
4. **Prefixes.**
   - After the row passes report done, `deletePrefix` runs for each folder `erase.prefixes(owner)` returns.
   - Each prefix must contain the owner as a whole path segment, raw or URI-encoded, or the call answers
     `INVALID_CONFIG`. So `() => ["avatars/"]` can never wipe every owner.
5. **Finish.** `erased_at` is set.
6. **The sweep carries unfinished erasures.**
   - A new pass, after the expire pass, continues every marked owner with the sweep's grace and signal. An app calls
     `eraseOwner` once at account deletion and keeps its sweep schedule.
   - `reopenOwner` clears the mark, for a reused owner id or a mistake. Files already deleted stay deleted.
7. **Finding owners that no longer exist stays the app's.** cloudrop cannot join the app's user table, and a callback
   would push every owner through JavaScript on every sweep. The guide gives the anti-join (part 7) and the loop.

**Schema.**
- Postgres:
  ```sql
  ALTER TABLE cloudrop_usage ADD COLUMN erase_requested_at timestamptz(3), ADD COLUMN erased_at timestamptz(3);
  CREATE INDEX cloudrop_usage_erasing_idx ON cloudrop_usage (owner)
    WHERE erase_requested_at IS NOT NULL AND erased_at IS NULL;
  ```
- SQLite and D1: integer columns.
- Prisma: the partial index through `--create-only`, as the guide does for CHECK constraints.
- `checkSchema` requires the columns. An unmigrated database fails at start with `INVALID_CONFIG` naming the exact SQL.

**Store interface.** `reserve` gains the `"erased"` outcome, and there are four new required methods: `markErasure`,
`erased`, `reopen` and `erasing`. A hand-written store must add them at 1.0; the changelog says so.

**Edge cases the guide states:**
- Rows of owner-less routes are never reached.
- A completion already running finishes, and the next pass deletes it. Its `onComplete` may run for an account being
  erased.
- An untracked multipart upload is left to the lifecycle rule, which `checkBucket` checks.

**Tests.**
- **Store contract on every backend** (unit, `test:db`, `test:wrangler`). Each row:
  - the mark creates a zero row and keeps its first time;
  - `reserve` after the mark writes nothing, with and without a limit or a request key;
  - `erased` is guarded on `requestedAt`;
  - `reopen` clears the mark;
  - `erasing` pages by keyset.
- **A Postgres race row** in the style of `lock-order.db.integration.test.ts`: reserve holding the usage lock, against
  the mark on another connection.
- **Server rows on the fake R2.** Each row:
  - an `/upload` whose `authorize` resolved before the mark answers `FORBIDDEN`, with a fault probe that removes the
    guard;
  - prefixes go only after the rows;
  - an unsafe prefix is refused;
  - the sweep reaches `erased_at`;
  - `reopenOwner` lets uploads in again.

## 5. The store's code ships with the store (`M12-S`, `docs/decisions/m12-store-entry.md`)

**Problem.** A stateless server carries the store's code: about 7.3 kB of the 34.71 kB bundled server, measured
2026-11-22 (`M5-T69` recorded 4.93 kB). Part 4 would add about 1.3 kB more and pass the 36 kB ceiling.

**Build: injected through the store object, with no new import on the simple path.**
- **The store paths.** `src/store/paths.ts` implements a type-only `StorePaths` interface with the store modules:
  - `store-upload`, `store-complete`, `store-calls`, `store-api`;
  - `erase`, `sweep`;
  - `owner-files`, `all-files`, `store-delete`, `leftovers`;
  - the quota and lease checks.
- **How they reach the server.**
  - `sqlStore`, which every shipped adapter goes through, attaches them under `Symbol.for("cloudrop.store")`. So does
    `memoryStore`.
  - The property is enumerable and attached after the transaction spread, so a store wrapped with spread keeps it.
  - The core endpoints call `config.paths?.…` instead of importing the store modules.
- **New entry `cloudrop/store`.** It exports `defineStore(methods)` for a hand-written store, plus the store types.
  - A store object without the paths answers `INVALID_CONFIG`, telling the developer to wrap it with `defineStore`.
  - A version field refuses paths from another installed copy of cloudrop.
- **Budgets.**
  - The bundled `cloudrop` ceiling drops from 36 to 30 kB; it measures about 27.4 kB after the split.
  - The adapters' summed budgets rise by the store code they now carry, to measured plus about 8 %.
  - A new bundled budget, `cloudrop` plus `cloudrop/adapters/sql`, guards what a store app ships.
  - The owner confirms the new ceilings in the release summary.
- **Tests.**
  - `check-package.sh` proves `dist/index.js`'s chunk graph holds no store module, by grepping for a message only the
    erasure has.
  - Unit rows: the stub answers `INVALID_CONFIG`; `defineStore` works; a store wrapped with spread still works.
  - Every store lane runs unchanged.

## 6. Names frozen at 1.0 (`M12-A`, `docs/decisions/m12-api.md`)

Each change lands before the freeze, with an "Upgrading to 1.0" entry in the changelog.

| Today | 1.0 | Why |
|---|---|---|
| `FileStatus` from `cloudrop` (a row status) beside `FileStatus` from `cloudrop/client` (a file state) | `FileRecordStatus` for the row | Two frozen types with one name and different members |
| `api.delete`, `deleteMany`, `head`, `copy`, `put` (by key) beside `api.deleteFile` (by id) | `deleteObject`, `deleteObjects`, `headObject`, `copyObject`, `putObject` | With a store, `api.delete(file.key)` skips the row and the quota while looking like the same operation |
| `revokeUploads({ owner })` | `revokeUploads(owner)` | One convention with `usage(owner)` and `eraseOwner(owner)` |
| `namespace` and `account`, both the user's id | `namespace` defaults to `account` when it is a string | The examples pass both; must land before 1.0 because it moves where resume records are found |
| `useUpload().resume(upload, file)` beside `resume()` that un-pauses | `resumeUpload(upload, file)` | One name, two meanings |
| `discarding: ReadonlySet<string>` | `discardingIds` | Reads as a boolean |
| `STORAGE_ERROR` for both bucket failures and the browser's IndexedDB | `BROWSER_STORAGE_ERROR` for the browser's | Two different fixes behind one code |
| The `authorize` result spread into every route context, only `request`, `metadata`, `file` reserved | Also reserve `data`, `tx`, `route`, `signal`; a collision is a type error | Adding a context field after 1.0 would break apps whose `authorize` returns that name |
| `createCloudrop({ storage })` required | Defaults to `r2()`, which reads `CLOUDROP_R2_*` lazily (`M4-F17`) | One line less on the simple path; the missing-settings error already names the variables |
| A route without `prefix` writes at the bucket root | The route's name is the default first key segment | No silent mixing at the root; a whole route can be found by prefix |
| `config.ts` message suggests `plugins: [limits()]` | `[contentChecks()]` | The plugin does not exist |

**Kept, with reasons recorded:**
- `allowAnyone` beside `unauthorized()`/`forbidden()`: a function, against return values.
- `onComplete` beside `afterComplete`: inside the completion and repeatable, against once after the record.
- `visibility`, `multipartThreshold` (documented as MiB) and `completionLeaseMs`.
- `getUrl({ download })`, and `expiresIn` in seconds (S3's convention, documented).
- `NO_SUCH_UPLOAD` beside `UPLOAD_EXPIRED`, and `INVALID_TOKEN`.

**Stability tiers:**
- **Implemented by apps:** `StorageDriver`, `CloudropStore`, `SqlExecutor`. They may gain optional members in a minor
  and required members only in a major.
- **The plugin API** (`CloudropPlugin`, `ServerHooks`, `extendRoute`) is marked `@experimental`, outside semver. It has
  one user, and the plugins it was designed for are cut.
- **The 20 wire types** from `cloudrop/client` change only with the protocol.

**The quickstart after this part.** About 32 lines in four files:

```ts
// lib/cloudrop.ts
import { createCloudrop, route, unauthorized } from "cloudrop";

export const cloudrop = createCloudrop({
  routes: {
    avatar: route({
      accept: "image/*",
      maxSize: "5MB",
      authorize: async ({ request }) => {
        const user = await getUser(request);
        return user ? { userId: user.id } : unauthorized();
      },
    }),
  },
});
```

Then:
- the Next handler (3 lines);
- the hooks (3 lines);
- a component of about 12 lines;

## 7. The tables are a contract (`M12-Q`, `docs/decisions/m12-tables.md`)

Apps rightly query `cloudrop_files` and `cloudrop_usage` for admin views: the pilot's inventory, its usage page, and
its stuck completions, which it finds as `status = 'failed' AND claimed_at IS NOT NULL`. 1.0 makes that reading safe.

**Guaranteed under semver for reading:**

| Table | Columns |
|---|---|
| `cloudrop_files` | `id` (a ULID, sorts by creation to the millisecond), `route`, `key`, `owner`, `status`, `name`, `type`, `size`, `metadata`, `result`, `claimed_at`, `expires_at`, `created_at`, `completed_at`, `ended_at`, `cleaned_at` |
| `cloudrop_usage` | `owner`, `reserved_bytes`, `active_bytes`, `files`, `erase_requested_at`, `erased_at` |

- Every guaranteed column has the meaning and the per-status invariants of part 3b.
- `updated_at` is guaranteed weakly: it is not a watermark.
- **Internal:** `upload_id`, `claim`, `request_key`, and the index names. That the indexes exist is guaranteed.

**A new "Your own queries" section in `docs/guide/store.md`.** It replaces "read the tables freely" and covers:
- **What is guaranteed.** Any change to a guaranteed column is a major release.
- **Reading safely:**
  - snapshots per statement;
  - SQLite times are integer milliseconds;
  - drivers return `size` as text;
  - order by `created_at, id`;
  - keys are NFC;
  - owner-less rows exist.
- **Recipes:**
  - an admin inventory joined with the app's users;
  - stuck completions;
  - failures of the last day;
  - per-owner usage;
  - the anti-join for owners who no longer exist, followed by `eraseOwner`.
- **Never write.**
  - No `INSERT` or `UPDATE` on either table, and no `DELETE` on usage rows: they hold the quota and the erase mark.
  - Drift is fixed with `api.reconcile`.
  - The only allowed delete is a retention purge of ended, cleaned rows (`aborted`, `rejected`, `expired`, `deleted`
    with `cleaned_at` set), never `failed` rows with a claim, and the rows of an erased owner.

## 8. Release documentation and guards (`M12-P`, `docs/decisions/m12-policy.md`)

- **Stability and versioning** (`docs/guide/stability.md`):
  - **Covered by semver:**
    - the entries and their exports;
    - documented behaviour;
    - error codes and their statuses;
    - the wire protocol;
    - the token format (`v: 1`) and the IndexedDB format;
    - the guaranteed columns;
    - the command's flags and exit codes.
  - **Not covered:** message text, log lines, bundle size, anything undocumented.
  - **Allowed in a minor:** new error codes and union members (apps keep a default branch), new optional options,
    additive migrations with their SQL in the changelog, refined error classification.
  - **Deprecation:** `@deprecated` plus one logger warning, kept at least one minor and six months.
  - **Wire compatibility:** any client and server of one major work together in both directions (cached bundles,
    rolling deploys, 24-hour tokens). A major accepts the previous token version for 24 hours.
  - **Runtimes:**
    - Node 26 or newer (the owner's floor), Bun 1.4, Workers and Deno, each in CI. Deno gets a smoke lane.
    - Browsers: Chrome 103, Firefox 100, Safari 16 (`M4-F6`).
    - React 18 and 19.
    - TypeScript 7.0 or newer (the owner's floor). A CI job type-checks the packed types with 7.0.0.
- **Threat model** (`docs/guide/security.md`, base spec §13):
  - assets, actors and trust boundaries;
  - each control of base spec §7;
  - what is left to the app: rate limiting, malware scanning, decompression bombs, integrity beyond size and type,
    session security;
  - the residual risks: a token outlives a revoked session by up to 24 hours; without a store `/abort` can delete a
    completed file; private visibility only warns; a persisted token sits in IndexedDB.
  - It links `SECURITY.md`.
- **Content scanning recipe** in `docs/guide/plugins.md`.
  - A ten-line `afterVerify` plugin. It already works: a returned `CloudropError` deletes the object and ends the row
    `rejected`, while a throw keeps the object and answers a retryable `SERVER_ERROR`, so a scanner outage fails closed.
  - The guide states the 120 s `/complete` budget, `visibility: "private"`, and `VERIFICATION_FAILED`.
  - A guide test runs the recipe on the fake R2.
- **Framework recipes** in `docs/guide/server.md`, each verified against the framework's docs, and run locally where
  marked:
  - SvelteKit `fallback`;
  - React Router 7 `loader` plus `action`;
  - Astro `ALL`;
  - Nuxt/Nitro (h3 v1 `toWebRequest`, h3 v2 `e.req`);

## 10. How it is built and released

1. **Foundation first:** part 5 (size room), part 3 (types), then part 6 (names). Every later part builds on them.
2. **Then, in parallel by file ownership:**
   - part 1 (React);
   - part 2a to 2c (server refusals);
   - part 2d (client classifier);
   - part 4 (erasure, after part 5);
   - part 7 (docs).
3. **Part 8 last:** its reference and freeze guard read the finished surface.
4. **A review of every changed area**, by reviewers who must prove each finding with a failing test or a measurement.
   Every proven finding is fixed (`M12-R`).
5. **All gates:**
   - `verify`, `test:db`, `test:wrangler`, `test:rustfs`, `test:live`, `test:chaos`, `test:browser`,
     `test:browser:live`;
   - `check-drizzle-versions.sh`;
   - the new Deno smoke and TypeScript 7.0.0 floor jobs, every job on Node 26.
6. **The pilot moves to the packed candidate.** It must pass all its gates, and it removes, as the acceptance proof:
   - `start-refusals.ts`;
   - its copied refusal lists;
   - the auth-object smuggling and its guards (`isUploadActor`, `deleterOf`);
   - the `totals.done` ref;
   - `erasure.ts` and its `storage_erasure` table.

   Every gap it finds is fixed before release (`release-only-after-pilot-and-owner`).
7. **An ELI5 summary for the owner,** including the new size ceilings. Then the owner's explicit "release", then
   `1.0.0` from the tag.
