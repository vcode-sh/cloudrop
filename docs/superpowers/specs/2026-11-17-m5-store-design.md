# M5: the database store

Date: 2026-11-17. Status: approved by the owner on 2026-11-17 ("build the store interface before the M5 plugins"),
under the standing instruction to follow the best recommendations without check-ins. Decisions: series `M5-T` in
`docs/decisions/m5-store.md`. This milestone takes the number M5; the plugins move to M6 and docs/beta/1.0 to M7
(spec §14 is amended in the same change).

## 1. Why, and the evidence

The product-fit review of 2026-11-17 found that in the owner's apps (app-b on Prisma, app-c and app-a on Drizzle) the
hard part of uploads is not the transfer but the database around it. app-b and app-c each built, by hand, the same
shape: a row per upload written before anything is signed, a guarded state transition at completion so the app's
completion work runs once, quota reserved and committed atomically, and a sweep that ends what was never finished.
Their incidents are the design's test cases:

- app-b deleted a pending row when an early `/complete` saw no object yet, leaving the later PUT as an orphan; it
  reused a status column as a lock token; its quota check at presign could be overshot before confirm.
- app-c ran storage calls inside a database transaction holding row locks; deleted 2,522 live objects when a reference
  table was missing from its sweep; held reserved bytes until physical deletion.
- Both treat a lost acknowledgement (storage completed, database not updated) as the case to survive.

Library research (better-auth, Auth.js, Lucia, Payload, UploadThing, tus) found: one core with narrow, domain-specific,
single-statement adapter methods beats generic CRUD for a single table; exactly-once needs a conditional update whose
affected-row count is exact; HTTP Postgres drivers and Cloudflare D1 have no interactive transactions; Prisma 8 (RC)
replaces the generated client. The code study found six seams in the server where store calls fit, each behind
`if (config.store)`, leaving the stateless mode byte-for-byte unchanged.

## 2. Goals and non-goals

Goals:
1. **Opt-in.** `createCloudrop({ store })`. Without a store nothing changes: same requests, same answers, same tests.
2. **A row before signing.** `/upload` writes one row per accepted file before any URL is signed or any multipart
   upload is created; a row that cannot be written refuses that file.
3. **`onComplete` once.** A guarded transition decides the one `/complete` that runs `onComplete`; retries and
   overlapping completions get the stored result without running it again. With a transactional adapter the
   transition, `onComplete`'s database writes and the result commit together (exactly once for database work); without
   one, a lease makes it run again only after a crash past the lease (stated plainly in the docs).
4. **Hard quota.** Per owner, reserved at `/upload` by a guarded increment, committed at `/complete` with the stored
   size, released on abort, rejection, expiry and deletion. Concurrent uploads cannot overshoot it.
5. **Revocation.** An aborted row blocks later `/sign` and `/complete`; `/abort` never deletes a completed file;
   `api.revokeUploads({ owner })` stops a signed-out user's unfinished uploads at their next call.
6. **A sweep that cannot destroy live data.** Row-driven, bounded, cursor-paged, idempotent; deletes only objects whose
   `cloudrop-id` matches a row that never completed; never touches completed rows or keys without a row.
7. **Adapters** for Prisma 7, Drizzle (Postgres and SQLite drivers) and raw SQL executors (node-postgres, postgres.js,
   `node:sqlite`/`bun:sqlite`, Cloudflare D1), all from one SQL core, proven by one contract suite on real databases.

Non-goals: MySQL (no `RETURNING`; later), Prisma 8 until it is stable (the executor seam allows it), MongoDB, a CLI
schema generator (docs ship the schema; a generator can share a bin with the planned bucket-setup command later),
derivatives, domain links (the app's), bucket-driven orphan scans (report-only tools later), cross-device resume.

## 3. Data model (`M5-T1`)

Two tables. Table names are configurable (`{ tables: { files, usage } }`, defaults `cloudrop_files`,
`cloudrop_usage`); column names are fixed snake_case (Prisma users map fields with `@map`). Postgres types shown;
SQLite uses `TEXT`/`INTEGER` (milliseconds for times) with the same names.

`cloudrop_files`:

| Column | Type | Meaning |
|---|---|---|
| `id` | `text` primary key | The file id cloudrop already puts in the token and the object's `cloudrop-id` (a ULID). Generated by cloudrop before the insert, so serial ids are impossible by design. |
| `route` | `text` not null | Route name. |
| `key` | `text` not null unique | Object key. |
| `owner` | `text` null | From the route's `owner(auth)` callback; null when the route defines none. |
| `status` | `text` not null | `pending`, `completing`, `completed`, `aborted`, `rejected`, `failed`, `expired`, `deleted`. |
| `name`, `type` | `text` not null | Normalized file name and content type as signed. |
| `size` | `bigint` not null | Declared size (what quota reserved). |
| `stored_size` | `bigint` null | Verified size at completion. |
| `upload_id` | `text` null | Multipart upload id, written right after it is created. |
| `metadata` | `text` null | Validated metadata as JSON (≤ 2 KiB, the existing cap). |
| `result` | `text` null | `onComplete`'s JSON result (≤ 16 KiB; larger is a server error at completion). |
| `claim` | `text` null | The claim token of the `/complete` that holds `completing`. |
| `claimed_at` | `timestamptz` null | When the claim was taken (lease start). |
| `expires_at` | `timestamptz` not null | The token's expiry. |
| `created_at`, `updated_at` | `timestamptz` not null | |
| `completed_at`, `ended_at` | `timestamptz` null | Completion; any terminal non-completed state or deletion. |

Indexes: `(status, expires_at)`, `(owner, status)`.

`cloudrop_usage` (only written when `quota` is set): `owner text primary key`, `reserved_bytes bigint not null`,
`active_bytes bigint not null`, `files integer not null`, `updated_at timestamptz not null`, with `CHECK` ≥ 0 on the
three counters in Postgres.

The docs ship, for each dialect: a Prisma model snippet, Drizzle table definitions (also exported from
`cloudrop/adapters/drizzle` as `cloudropTables({ files, usage })` for `pg` and `sqlite`, so the app can query them
typed and include them in its migrations), and plain SQL DDL. Each adapter checks the schema once, lazily, with a
`SELECT <every column> FROM <table> WHERE 1 = 0`, and fails with `INVALID_CONFIG` naming the table and the first missing
column.

## 4. The store interface (`M5-T2`)

Public, so an app can write its own; every method is one atomic statement (or one batch) and returns `Result`, never
throws for an expected failure. Times are passed in by the server (its injected clock), so tests are deterministic;
the lease and the sweep grace are minutes, far above normal clock skew between servers (stated as a known cost).

```ts
type FileStatus = "pending" | "completing" | "completed" | "aborted" | "rejected" | "failed" | "expired" | "deleted";

interface NewFile { id: string; route: string; key: string; owner: string | null; name: string; type: string;
  size: number; metadata: string | null; expiresAt: Date }

interface FileRecord extends NewFile { status: FileStatus; storedSize: number | null; uploadId: string | null;
  result: string | null; createdAt: Date; completedAt: Date | null; endedAt: Date | null }

type ClaimOutcome =
  | { kind: "claimed" }
  | { kind: "completed"; record: FileRecord }      // replay: answer the stored result, run no hook
  | { kind: "busy" }                              // another /complete holds an unexpired claim
  | { kind: "ended"; status: FileStatus }          // aborted, rejected, failed, expired, deleted
  | { kind: "missing" };

interface CloudropStore<TTx = never> {
  /** One /upload: inserts each file as `pending`; with a quota, reserves each file's size for its owner by a guarded
   *  increment in order, so files that fit are accepted and later ones get QUOTA_EXCEEDED. Index-aligned result. */
  reserve(files: readonly NewFile[], quota: ((owner: string) => number | null) | null, now: Date):
    Promise<Result<readonly (CloudropError | null)[]>>;
  attach(id: string, uploadId: string, now: Date): Promise<Result<void>>;
  get(id: string): Promise<Result<FileRecord | null>>;
  claim(id: string, claim: string, now: Date, leaseMs: number): Promise<Result<ClaimOutcome>>;
  /** `completing` with this claim → `completed`; moves the reservation to active bytes with the stored size. */
  complete(id: string, claim: string, done: { storedSize: number; result: string | null }, now: Date):
    Promise<Result<boolean>>;
  /** Conditional transition from one of `from` to a terminal status; releases reserved bytes (from pending or
   *  completing) or active bytes (completed → deleted). Returns the record as it was, or null if no row matched. */
  end(id: string, from: readonly FileStatus[], to: Exclude<FileStatus, "pending" | "completing" | "completed">,
    now: Date): Promise<Result<FileRecord | null>>;
  /** Rows the sweep may end: pending/failed past `expiresBefore`, completing whose claim is older than the lease. */
  stale(expiresBefore: Date, claimedBefore: Date, limit: number, cursor: string | null):
    Promise<Result<{ records: FileRecord[]; cursor: string | null }>>;
  revoke(owner: string, now: Date): Promise<Result<number>>;    // pending → aborted for one owner
  usage(owner: string): Promise<Result<{ reservedBytes: number; activeBytes: number; files: number }>>;
  reconcile(owner: string | null): Promise<Result<number>>;     // recount usage from rows; returns owners fixed
  /** Present when the adapter can run app code in a database transaction. */
  transaction?: <T>(run: (tx: TTx, store: CloudropStore<TTx>) => Promise<T>) => Promise<T>;
}
```

`src/testing/memory-store.ts` implements it for the unit lane (exact same semantics, single-threaded atomicity).

## 5. Server behaviour with a store (`M5-T3` to `M5-T9`)

Every rule below applies only when `store` is configured; the stateless path is untouched and its tests pass unchanged.

- **Token (`M5-T3`).** The payload gains `stored: true`. A token without it (issued before the store was enabled)
  takes the stateless path until it expires; a token with it whose row is missing is refused as revoked.
- **`/upload` (`M5-T4`).** After `beforeUpload` (and its new per-file refusals, below), before any signing:
  `store.reserve` for the accepted files; files it refuses become rejected tickets through the existing per-file path,
  and plugins that accepted them get `onAbort("rejected")`. After `createMultipart`, `store.attach`. A file that fails
  to start: `store.end(id, ["pending"], "failed")`. A store failure on `reserve` refuses those files with a retryable
  `STORAGE_ERROR`-class code (`SERVER_ERROR`, retryable) and nothing is signed for them.
- **Per-file refusal in `beforeUpload` (`M5-T5`).** A plugin's `beforeUpload` may return an array aligned with
  `files`, each entry a `CloudropError` or `undefined`, refusing single files; returning one error still refuses the
  whole call. This is the quota hook for plugins and for apps without a store.
- **`QUOTA_EXCEEDED` (`M5-T6`).** New error code, 403, not retryable, per file, with a message that says the storage
  limit is reached and to delete files or ask for more space. Added to the protocol, the client's codes and the docs.
- **`/sign` (`M5-T7`).** After the token verifies (never before: a forged token costs no read), `store.get`; anything but
  `pending` is refused with `UPLOAD_EXPIRED` and its own message ("This upload was cancelled or has expired. Start it
  again."), also for a missing row whose token says `stored`. The client already treats `UPLOAD_EXPIRED` as needing a
  new ticket, so a retry goes back through `/upload` and `authorize`.
- **`/complete` (`M5-T8`).** Storage verification and `afterVerify` run first, outside any transaction (no network I/O
  inside one). Then:
  - with `store.transaction`: one transaction runs `claim` → `onComplete({ …, tx })` → `complete`; if `onComplete`
    throws, the transaction rolls back (the row stays `pending`) and the answer is the existing retryable error;
  - without: `claim` with a lease (default 5 min, above the client's 120 s deadline) → `onComplete` → `complete`; if it
    throws, `end` is not called and the claim's lease expires, so a retry runs it again.
  - `completed` → answer the stored `result` and file, run nothing; `busy` → retryable `SERVER_ERROR` (the client keeps
    the file as possibly complete and sends no `/abort`); `ended`/`missing` → `UPLOAD_EXPIRED` as for `/sign`.
  - A refusal by `afterVerify` or verification: `discard` as today, then `end(id, ["pending"], "rejected")`.
  - Storage completed but the database write failed: retryable answer; the retry finds the object (the existing
    `completedBefore` path), claims again after the lease, and completes.
  - New route callback `afterComplete(context)` (in the callbacks argument): runs after the completion committed, for
    side effects outside the database (email, queues); at-least-once, like hooks today.
  - The adapter's `route` property is the same `route()` with `onComplete`'s context typed to carry the adapter's `tx`
    (runtime identical); apps that do not need `tx` keep importing `route` from `cloudrop`.
- **`/abort` (`M5-T9`).** `end(id, ["pending"], "aborted")` first. If the row was `completed` or `completing`, the
  answer is `ok` and nothing is deleted and no `onAbort` runs (closes the 24-hour delete capability of M2-X1/M2-D20 for
  store users); otherwise the existing abort-and-delete runs.
- **Owner.** New route callback `owner(context) => string` (callbacks argument, typed from `authorize`). Without it the
  row's owner is null and quota does not apply to that route.
- **Quota option.** `createCloudrop({ store, quota: (owner) => number | null | Promise<…> })`, bytes per owner (null:
  unlimited). It is read once per owner per `/upload`.

## 6. File API with a store (`M5-T10`)

`cloudrop.api` gains, only with a store (calling them without one resolves `INVALID_CONFIG`):
- `file(id)` → the record; `usage(owner)`; `deleteFile(id)` (completed → deleted, then deletes the object by the stored
  key, releasing active bytes; idempotent); `revokeUploads({ owner })`; `reconcile({ owner? })`.
- `sweep({ limit = 100, cursor, grace = 1 h })`: for each stale row, oldest first: abort its multipart upload (idempotent),
  HEAD the key and delete the object only if its `cloudrop-id` equals the row id, then `end(id, [status], "expired")`
  (which releases quota). A `completing` row whose lease expired more than `grace` ago is reported, not deleted (its
  `onComplete` may have recorded the file). Returns `{ ended, reported, cursor }`. Bounded per call so Workers can run it
  from a cron trigger; scheduling is the app's.

## 7. Adapters (`M5-T11` to `M5-T14`)

- **SQL core (`M5-T11`).** Internal, dialect-aware (Postgres, SQLite): builds every statement of §4 as parameterized SQL
  with `RETURNING` and counts by returned rows; table names quoted and validated (`^[A-Za-z_][A-Za-z0-9_]*$`). It takes
  an executor `{ query(sql, params): Promise<rows>, transaction?(run) }`.
- **`cloudrop/adapters/sql` (`M5-T12`).** `sqlStore(executor, { dialect, tables? })` with ready executors documented for
  node-postgres, postgres.js, `node:sqlite`/`bun:sqlite` and D1 (`prepare().bind().all()`; no transactions, so the lease
  path).
- **`cloudrop/adapters/drizzle` (`M5-T13`).** `drizzleStore(db, { dialect, tables?, transaction? })` over the core using
  Drizzle's raw `sql` execution, `transaction: true` wrapping `db.transaction(tx => …)` and passing Drizzle's `tx`;
  `cloudropTables()` exported. `drizzle-orm` optional peer.
- **`cloudrop/adapters/prisma` (`M5-T14`).** `prismaStore(prisma, { dialect, tables?, transaction? })` over the core using
  `$queryRawUnsafe` (structurally typed client, no import of `@prisma/client`), `transaction: true` wrapping
  `prisma.$transaction(async tx => …)`. Prisma 7.
- Packaging follows `cloudrop/react`: subpath exports, optional peers, biome fence (the core never imports an adapter),
  own size budgets (≤ 3 kB each bundled, under the M4-F24 rule).

## 8. Tests and lanes (`M5-T15`)

- **Store contract suite** `src/testing/store-contract.ts` (+ case files), run against the memory store in the unit lane
  and against every adapter in `test:db`: reserve (order, quota boundaries exact to the byte, concurrent reserves never
  overshoot), attach, claim races (N concurrent claims, exactly one `claimed`), lease expiry, stale claim cannot
  complete, complete/end transitions and usage arithmetic, replay returns the stored record, revoke, stale paging and
  limit, reconcile repairs drift, table-name mapping, schema check message, transaction rollback (the app row is absent
  and the file is claimable again). Results are read back through a raw reader, not the adapter under test. Declared
  gaps (`transactions` for D1) skip with a reason, as the storage contract does.
- **Server tests** on the fake R2 with the memory store for every rule in §5 and §6, including the M4-F12 overlapping
  completions (one `onComplete`), abort after completion (nothing deleted), revocation, quota refusal per file, sweep
  safety (completed rows and foreign keys never touched).
- **`bun run test:db`**: Postgres in Docker (label `cloudrop.test`, port `19500` by default, `CLOUDROP_POSTGRES_PORT`),
  SQLite via `node:sqlite`; runs the contract for sql (node-postgres, postgres.js, node:sqlite), Drizzle (node-postgres,
  postgres.js, sqlite) and Prisma 7 (Postgres, SQLite). Fails, never skips, without Docker. D1 runs the contract in the
  Wrangler lane.
- **Chaos lane:** rows with a store: faults on `/complete` and overlapping retries still run `onComplete` once and leave
  usage exact.
- **Example:** `examples/next` gains an opt-in store (SQLite through Drizzle) showing `owner`, `quota` and
  `afterComplete`; a browser row proves a reload-and-resume completes once.
